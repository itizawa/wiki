# コード品質を改善して PR にする

改善箇所を探し、issue は作らずに、そのまま TDD でリファクタリングして PR にする。**挙動は変えない。** 挙動が変わっていないことは、実装した本人ではなく、別のサブエージェントが確かめる。

役割を分ける。

- **自分（親）**: 範囲を決める、探すサブエージェントに配る、候補をまとめて絞る、実装のサブエージェントに配る、レビューのサブエージェントに配る、差し戻しの取り次ぎ、結果の報告
- **探す人**（`Explore`）: 割り当てられた範囲を読み、改善候補を決まった形で返す。コードは変えない
- **実装する人**（`general-purpose`、worktree）: 1 候補につき 1 体。テストを先に書き、リファクタリングし、PR を作る
- **レビューする人**（`general-purpose`、実装した人とは別の新しいエージェント）: PR の差分を、実装した人の説明を信じずに検証する。直さない

PR は作るところまで。マージは人が行う。

依頼文のひな形は `references/` にある。

- `references/smells.md` — 探す観点と、このリポジトリで手を付けないもの
- `references/finder-prompt.md` — 探す人への依頼文
- `references/implementer-prompt.md` — 実装する人への依頼文
- `references/reviewer-prompt.md` — レビューする人への依頼文

## 進め方

### 1. 範囲を決める

頼まれた内容から決まらなければ、`AskUserQuestion` で 1 回にまとめて聞く。

- **どこを見るか**: `apps/api` / `apps/admin` / `apps/site` / `apps/worker` / `packages/shared` / 全部（おすすめ: 全部）。ディレクトリやファイルを指定されたら、それだけにする
- **PR の数の上限**: 3 / 5（おすすめ）/ 8。1 PR は小さくするので、数で量を決める

聞いたあとは確認を挟まず最後まで進める（即 PR にすることは頼まれている）。

### 2. 改善箇所を探す

範囲を 3〜5 の組に分け（例: `apps/api/src/routes` と `apps/api/src/*` の残り、`apps/admin/src/routes`、`apps/admin/src/components`、`apps/site` と `apps/worker`、`packages/shared`）、`Explore` のサブエージェントを **1 つのメッセージで同時に** 起動する。依頼文は `references/finder-prompt.md`。

各候補は、次を持って返ってくる。

- 場所（ファイルと行）
- 観点（`references/smells.md` のどれか）
- 何が困るか、どう直すか
- いまのテストが、その挙動を押さえているか（押さえていなければ、特性テストを足す必要がある）
- 大きさ（触るファイル数、変える行数の見込み）
- 挙動が変わりうる点（公開している型・API の形・エラー文言・順序・副作用）

### 3. 絞る

候補を集めて、次の順に絞る。

1. **同じ原因はまとめる**。1 つの PR で直す単位にそろえる
2. **挙動が変わるものは落とす**。バグ修正、仕様の変更、機能の追加はこのスキルの対象外。見つけたものは、最後の報告に「別件として見つけたこと」で書く（issue は作らない）
3. **大きいものは落とす**。1 PR で、触るのは多くても 5 ファイル・差分 300 行ほど。これを超えるなら、独立して直せる単位に割れるものだけ割って残し、割れなければ落とす
4. **すでにある PR と衝突するものは落とす**。`gh pr list --state open --json number,title,files` を見る
5. **効果の大きい順**に並べ、上限の数まで取る
6. **PR どうしで同じファイルを触るものは、同じチェーンに入れる**（直列）。そうでないものは並行

### 4. 実装する（TDD）

候補ごとに、`Agent`（`subagent_type: "general-purpose"`、`isolation: "worktree"`）を起動する。依頼文は `references/implementer-prompt.md`。

- **同時に動かすのは 3 本まで。** それより多いと、この Mac ではテストが時間切れで落ちる
- チェーンの 2 番目以降は、前の PR を作り終えてから起動し、前のブランチに積む（マージは待たない）
- ブランチ名は `claude/refactor-<英語の短い名前>`。起点は `origin/main`（先に `git fetch origin`。ローカルの `main` は古いことがある）

実装する人は、次の順で進める。

1. **特性テスト（赤にしない）**: 直す前のコードの挙動を固めるテストを書く。**直す前のコードで通る**ことを確かめる。いまのテストが十分に押さえているなら、足さない
2. コミットする（`test: …`）。これで、レビューする人が「直す前でも通るテストか」を確かめられる
3. **リファクタリング**: 小さい手順に分け、手順ごとに `pnpm --filter <対象> test` を通す（緑のまま進める）
4. **既存のテストの期待値は変えない。** 消さない、ゆるめない、`skip` しない。どうしても変えないと進めないなら、挙動が変わるということなので、止まる
5. `pnpm typecheck` と `pnpm test` を通し、push して PR を作り、CI を待つ

挙動を変えずに済むか迷う点は、自分で決めずに止まって聞く（`resolve-issues` の「迷ったとき」と同じ。親が `AskUserQuestion` で取り次ぐ）。

### 5. レビューする（別のサブエージェント）

実装の PR ができたら、**実装した人とは別の新しい** `general-purpose` サブエージェントを `isolation: "worktree"` で起動する。依頼文は `references/reviewer-prompt.md`。実装した人の経過や自己申告は渡さない（PR の番号だけ渡す）。

レビューする人は、挙動が変わっていないことを次で確かめる。

- 特性テストを、PR の**土台（base）のコードでも**走らせて通ること
- 既存のテストの期待値が、消えても弱まってもいないこと
- 差分を読み、公開している型・API の応答の形・エラー文言・順序・副作用・DB へのクエリが同じこと
- UI に触れていれば、変更前後で同じ画面になること（見た目が変わるなら、挙動が変わっている）
- `pnpm typecheck` と `pnpm test` が通ること
- リファクタリングに紛れ込んだ、関係のない変更が無いこと

返事は `## 承認` か `## 差し戻し`。結果は PR のコメントにも残させる（`gh pr comment`）。

**差し戻し**: 理由を `SendMessage` で実装した人に渡して直させ、直ったらまたレビューする人を**新しく**起動する。差し戻しは 2 回まで。それでも通らなければ PR を `gh pr close` せずに、そのまま「承認されなかった PR」として報告する。

### 6. 片付けて、報告する

- エージェントの作業ツリーを消す（`git worktree list` で今回のエージェントが使った `.claude/worktrees/` の下のものだけ `git worktree remove`）
- 立てたまま残したサーバーを止める

報告は表にする。

| PR | 内容 | 観点 | レビュー | CI |
|---|---|---|---|---|
| #301 | `routes/pages.ts` の重複した権限チェックを関数にまとめる | 重複 | 承認 | 通過 |
| #302 | … | … | 差し戻し 1 回 → 承認 | 通過 |

表の下に、次を書く。

- マージの順番（積んだ PR は先頭から）
- 落とした候補と理由（挙動が変わる、大きすぎる、衝突）
- **別件として見つけたこと**（バグかもしれない挙動など。issue は作っていない）
- 確かめられなかったこと

## 守ること

- **issue を作らない。** 見つけたら、そのまま PR にする
- **挙動を変えない。** 迷ったら、変えない
- **1 PR 1 テーマ。** 「ついでに」直さない
- 実装する人にレビューさせない。レビューする人に直させない
- UI のコンポーネントを触る PR は、`CLAUDE.md` の規則（一覧は `DataList` を使うなど）に沿う方向へだけ寄せる。見た目が変わるなら、このスキルの対象外
- PR・コミットの文は、日本語で、です・ます を使わずに書く

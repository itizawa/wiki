# 探す観点

## 直す対象

| 観点 | 見るところ | 直し方の例 |
|---|---|---|
| 重複 | 3 か所以上で同じ処理（権限チェック、クエリの組み立て、整形） | 関数・フックにまとめる |
| 長すぎる関数・コンポーネント | 1 つで複数の仕事をしている。80 行を超える、ネストが 3 段を超える | 仕事ごとに分ける、早期 return にする |
| 分かりにくい名前 | `data` `tmp` `flag`、略語、中身と合っていない名前 | 中身を表す名前に変える |
| 型の緩さ | `any`、不要な `as`、`!`、`string` で済ませている列挙 | 絞った型、`satisfies`、型ガード |
| 魔法の値 | 説明のない数字・文字列が複数個所に | 名前を付けた定数に |
| 死んだコード | 使われていない export・変数・分岐・コメントアウト | 消す（参照が無いことを `grep` と typecheck で確かめる） |
| 責務の混在 | 経路の関数の中に、検証・DB・整形・応答が全部ある | 層を分ける（既存の分け方に合わせる） |
| テストしにくい作り | 副作用と計算が絡んでいる | 計算を純関数に出す |
| 共通コンポーネントの未使用 | `DataList` を使わず `Table` を組んでいる（CLAUDE.md） | 共通コンポーネントに寄せる（見た目が変わらないときだけ） |

## 手を付けないもの

- バグの修正、仕様・文言・見た目の変更、機能の追加（挙動が変わる）
- DB のスキーマとマイグレーション（`apps/api` のマイグレーションは番号が続く）
- 依存の追加・更新（`renovate.json` が受け持つ）
- 公開している API の形（`apps/api` の応答、`packages/shared` の export の形）。内部の整理だけにする
- 生成物、`node_modules`、`.claude/`
- 好みの問題（書き方の流派が違うだけで、困りごとが説明できないもの）

## 良い候補の条件

- 何が困るかが 1 文で言える
- 直したあと、読む人が減らせるものが説明できる（行数、分岐、重複の数）
- テストで挙動を固められる
- 1 PR（5 ファイル・差分 300 行ほど）で終わる

## 進め方
1. `CLAUDE.md` と `README.md` を読む。UI を触るなら `/Users/itizawa/.claude/projects/-Users-itizawa-wiki/memory/ui-usability-checklist-50.md` も読む
2. `git fetch origin && git checkout -b <作るブランチ> <起点>`、`pnpm install`
3. **特性テスト**: 直す前のコードの挙動を固めるテストを書く。今のテストが十分に押さえているなら足さない。**直す前のコードで通る**ことを確かめる（赤から始めない。このテストは「挙動が変わっていないこと」の証拠になる）。正常系だけでなく、境界と失敗の場合（空、`null`、権限なし、エラー文言、順序）も固める
4. `test: …` でコミットする（リファクタリングと混ぜない。レビューする人が、このコミットだけを土台のコードに当てて通ることを確かめる）
5. **リファクタリング**: 小さい手順に分け、手順ごとに `pnpm --filter <対象> test` を通す。緑のまま進める。コミットも手順ごとに分ける（`refactor: …`）
6. **既存のテストの期待値は変えない**。消さない、ゆるめない、`skip` しない。テストの置き場所の移動や、名前の追従だけは可（それ以外はしない）。変えないと進めないなら、挙動が変わるということ。止まって `## 質問` で返す
7. 関係のない整形・ついでの修正をしない。1 PR 1 テーマ
8. `pnpm typecheck` と `pnpm test` を通す。API のテストが時間切れで落ちたら `pnpm --filter @wiki/api exec vitest run --testTimeout 60000` で確かめ直す
9. push して `gh pr create --base <PR の base>` で PR を作り、`gh pr checks <番号> --watch` で CI を待つ。落ちたら直す

## PR の本文
日本語で、です・ます を使わずに書く。

- 何を整理したか、なぜか（困っていたこと）
- **挙動が変わっていないことの根拠**: 足した特性テスト、既存のテストを変えていないこと
- どのコミットが `test`（直す前でも通る）で、どれが `refactor` か
- 確かめたこと / 確かめられなかったこと
- 自分で決めたこと

末尾に、次を付ける（コミットのメッセージにも）。

```
{{この会話で指定されている、コミット用と PR 用の帰属の行}}
```

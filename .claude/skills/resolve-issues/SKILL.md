# issue を PR にして解消する

自分は**指揮役**になる。issue を読んで順番を決め、1 issue につき 1 体のサブエージェントに実装から PR 作成までを任せ、質問の取り次ぎ・スクリーンショットの添付・結果のまとめを受け持つ。実装は自分では行わない。

PR は作るところまで。マージは人が行う。

## 進め方

### 1. 対象の issue を決める

- 番号が渡されていれば、それを対象にする
- 渡されていなければ `gh issue list --state open --limit 100` で一覧を出し、`AskUserQuestion` でどれを対象にするか聞く（ラベルやテーマでまとめた選択肢にする。例: 「セキュリティ（#177〜#182）」）
- 対象ごとに `gh issue view <番号> --comments` で本文とコメントを読む

次の issue は対象から外し、外した理由を最後の報告に書く。

- すでに PR がある（`gh pr list --state all --search "<番号> in:body"` で `Closes #<番号>` を探す）
- 子の issue を束ねるだけの親 issue（例: 「編集リクエスト」の #172 に対する #173〜#176）。子を対象にする

### 2. 依存を調べて、順番の案を作る

各 issue について、変えることになるファイルを実際にコードを読んで洗い出す（issue の「現状」「やること」にあるパスを出発点にする）。issue が多いときは `Explore` エージェントに並行で調べさせる。

次のどれかに当たる 2 つの issue は**依存あり**として、同じ**チェーン**（直列）に入れる。

- 本文に順番が書いてある（「この issue は #73 のあとに進める」、タイトルの ①②③④）
- 片方が作る仕組み（テーブル、API の経路、コンポーネント）を、もう片方が使う
- 同じファイルの同じあたりを両方が変える。別々に PR を作ると衝突する
- 両方が DB のマイグレーションを足す（`apps/api` のマイグレーションは番号が続くので、並行に作ると番号がぶつかる）

チェーンの中の順番は、土台になる方を先にする。どちらが先でもよいなら、番号の小さい方を先にする。

どれにも当たらない issue は、それぞれが長さ 1 のチェーンになる。チェーンどうしは並行に進める。

### 3. 始める前に、ユーザーに確かめる

順番の案を本文に書いて見せる。

```
並行して進めるチェーン（同時に動かすのは 3 本まで）
A: #177 → #181        （どちらもセッションまわりの `apps/api/src/auth/` を変える）
B: #178
C: #183 → #184 → #186 （Cron とビルド起動。#184 は #183 の再試行の仕組みを使う）
あとに回す: #179（A が終わって枠が空いたら始める）
```

そのうえで `AskUserQuestion` で聞く。

- この順番で始めてよいか
- issue の「決めること」に残っている点、読んでも一通りに決まらなかった点（1 回に 4 問まで。足りなければ続けて聞く）。答えは、その issue のエージェントへの依頼文に書き込む

### 4. サブエージェントに任せる

チェーンの先頭の issue を、`Agent`（`subagent_type: "general-purpose"`、`isolation: "worktree"`）で**1 つのメッセージにまとめて**起動する。依頼文は [`AGENT-BRIEF.md`](AGENT-BRIEF.md) を読み、`{{…}}` を埋めて作る。

- **同時に動かすのは 3 本まで。** それより多いと、この Mac ではテストが時間切れで落ちる。4 本目からは、どれかが終わったら始める
- **積む PR（チェーンの 2 番目から）:** 前の issue のエージェントが PR を作り終えたら、次のエージェントを起動する。マージは待たない。起点のブランチと PR の base は、前の issue のブランチにする
- **番号の割り当て:** エージェントごとに、重ならないポート（API は 8787 から、管理画面は 5173 から 1 ずつ増やす）と、スクリーンショットの置き場所（スクラッチパッドの `issue-<番号>/`）を渡す
- `Workflow` は使わない。途中で質問を取り次ぐために、`SendMessage` で続きを頼めるエージェントにする

### 5. エージェントの返事を受ける

エージェントの返事は、次の 3 つのどれかの見出しで始まる。

**`## 質問`** — 判断に迷って止まっている。書いてある選択肢を、そのまま `AskUserQuestion` でユーザーに聞く（どの issue の話かを質問文の頭に書く。例: 「#181: …」）。答えを `SendMessage` で同じエージェントに送り、続きを頼む。自分で答えを決めて返さない。ほかのエージェントは止めずに進める。

**`## 完了`** — PR ができた。次を順に行う。

1. `gh pr view <番号> --json baseRefName,headRefName,body` と `gh pr checks <番号>` で、base が指定どおりか、CI（`check`）が出ているかを見る。CI が出ていなければ衝突を疑う。CI が落ちていたら、同じエージェントに `SendMessage` で直させる
2. スクリーンショットがあれば PR に添付する（下の「スクリーンショットを添付する」）
3. チェーンに次の issue があれば、そのエージェントを起動する
4. 空いた枠で、あとに回していたチェーンを始める

**`## 中断`** — 進められなかった。理由をユーザーに伝え、`AskUserQuestion` でどうするか聞く（やり方を変えて続ける / この issue を飛ばす / チェーンの残りも止める）。チェーンの途中で飛ばすと、あとの issue は土台を失う。あとの issue を `origin/main` から始められるかは、その issue を読み直して決める。

### 6. 片付けて、報告する

全部のエージェントが終わったら、

- エージェントの作業ツリーを消す（`git worktree list` で `.claude/worktrees/` の下にあるもののうち、今回のエージェントが使ったものを `git worktree remove`）。この実行より前からあるものには触らない
- エージェントが立てたまま残したサーバーがあれば止める（渡したポートを `lsof -ti :<ポート>` で調べる）

報告は表にする。

| issue | PR | base | CI | 備考 |
|---|---|---|---|---|
| #177 | #201 | main | 通過 | |
| #181 | #202 | `claude/issue-177-…` | 通過 | #201 に積んだ PR |
| #179 | — | — | — | 飛ばした（理由） |

表の下に、次のことを書く。

- **マージの順番。** 積んだ PR は、チェーンの先頭から順にマージする
- **積んだ PR の注意。** 前の PR をマージしてブランチが消えると、GitHub が次の PR の base を `main` に付け替える。付け替わらなかったら `gh pr edit <番号> --base main` で直す。base が `main` でないままマージした PR は、`Closes #<番号>` があっても issue が閉じないので、手で閉じる
- ユーザーに聞いて決めたことと、聞かずにエージェントが決めたこと
- 確かめられなかったこと

## スクリーンショットを添付する

UI を変えた PR には、変更後（必要なら変更前も）のスクリーンショットを載せる（`CLAUDE.md` のルール）。撮るのはエージェント、添付するのは指揮役にする。Chrome は 1 つしか無く、並行するエージェントが同時に操作するとタブを取り合うため。

- エージェントは PNG をスクリーンショットの置き場所に保存し、PR の本文に `<!-- screenshot: after-list.png -->` の形で場所だけ空けておく
- 指揮役は、PR を 1 つずつ順に処理する。Chrome 拡張で PR のページを開き、コメント欄のファイル入力に画像を渡して `https://github.com/user-attachments/assets/…` の URL を得て、`gh pr edit <番号> --body-file` で本文の空けておいた場所に入れる。コメント欄は空に戻し、投稿はしない
- この Mac に `~/.claude/projects/-Users-itizawa-wiki/memory/pr-screenshots-via-chrome.md` があれば、細かい手順はそれに従う

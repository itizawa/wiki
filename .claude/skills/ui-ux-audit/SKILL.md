# UI/UX を点検して issue にする

実際のブラウザで画面を開き、幅を変えて表示崩れを探し、使っていて引っかかる点（UX）と、オブジェクト中心になっていない画面の組み立て（OOUI）も拾い、直せる単位の issue にする。

役割を分ける。

- **自分（親）**: 準備、ウィンドウの幅を変える、サブエージェントに画面を配る、結果をまとめる、重複を消す、ユーザーに確かめる、issue を作る
- **サブエージェント**: 割り当てられた画面を自分のタブで開いて点検し、見つけたことを決まった形で返すだけ。**issue は作らない**（重複と粒度は親がまとめて決める）

観点は `references/checklist.md`、サブエージェントへの指示のひな形は `references/agent-prompt.md`、崩れを数字で測るスクリプトは `references/layout-probe.js` にある。

## 進め方

### 1. 何を・どこで点検するかを決める

頼まれた内容から決まらなければ、`AskUserQuestion` でまとめて聞く（1回で）。

- **どこを開くか**
  - 本番（`https://wiki-admin.hatchery-works.com`、公開サイトは `https://{key}.hatchery-works.com`）（おすすめ: 準備が要らない）。**見るだけにする**（下の「本番で守ること」）
  - 手元（ユーザーの PC で `pnpm dev` した `http://localhost:5173`）。データを変える操作も試せる。クラウドのセッションでは、このコンテナの localhost はユーザーの Chrome から見えないので、ユーザーの PC で立ち上げてもらう
- **範囲**: 管理画面だけ / 公開サイトだけ / 両方。「一覧だけ」「エディタだけ」のように画面を絞ってもよい
- **幅**: 既定は下の「幅」の3つ。320px（最小）や 1920px を足すかどうか

本番で守ること（サブエージェントにも必ず渡す）:

- 保存・公開・予約・削除・招待・ロール変更・設定の保存をしない。メニューやダイアログは開いて「キャンセル」で閉じるところまで
- **エディタに文字を打たない**（下書きが自動で保存される）
- ブラウザのダイアログ（`confirm` など）を出しそうなボタンを押さない。出すと拡張機能が止まる

### 2. ブラウザを用意する

`anthropic-skills:chrome-browser` スキルを読んでから使う。

- Chrome の道具は1回の `ToolSearch` でまとめて読み込む: `tabs_context_mcp` `tabs_create_mcp` `tabs_close_mcp` `navigate` `computer` `read_page` `find` `get_page_text` `javascript_tool` `resize_window` `read_console_messages` `read_network_requests`
- `tabs_context_mcp` でいまのタブを見て、新しいタブを開く。拡張がつながっていなければ、そう伝えて止まる
- 管理画面を開き、ログインできているか確かめる。手元なら「開発用ログイン」（`DEV_LOGIN_EMAIL`）で入る。本番でログインしていなければ、ユーザーにログインしてもらう（代わりに Google の画面を操作しない）

### 3. 点検する画面を洗い出す（ブラウザの準備と並行で）

ブラウザを用意している間に、`Explore` のサブエージェントに次を調べさせる（コードを読むだけなので並行でよい）。

- 管理画面の画面の一覧: `apps/admin/src/router.tsx` の経路と、それぞれのコンポーネント（`apps/admin/src/routes/*.tsx`）
- 公開サイトの画面の一覧: `apps/site/src/pages/[wiki]/` の下（トップ、ページ `p/`、ツリー `t/`、検索、404、限定公開 `u/`）
- 幅で配置が変わるところ: `breakpoints`、`useMediaQuery`、`@media`（MUI の既定は sm 600px / md 900px / lg 1200px。サイドバーは md 未満で隠れる）
- `:hover` でしか出ない操作（スマホでは押せない）

返ってきた一覧から、実際に開く URL を作る。`$pageId` のような部分は、ブラウザでツリーや一覧を開いて実在する ID を拾う。長いタイトル、深い階層、中身の無い一覧（ゴミ箱が空など）のように、崩れやすい状態の画面も入れる。

### 4. 幅ごとに、画面をサブエージェントに分けて点検する

ウィンドウの大きさは同じウィンドウのタブ全部にかかる。だから **幅は1つずつ順に、画面は並行に** 点検する。

#### 幅

| 名前 | 中身の幅（CSS px） | 見るところ |
|---|---|---|
| スマホ | 375 | md 未満の配置。横にはみ出さないか、押しやすいか |
| タブレット | 768 | md（900px）の手前。PC 用の配置が窮屈になっていないか |
| PC | 1280 | ふつうの配置。余白、揃え、広がりすぎ |

足すなら: 320（WCAG 1.4.10 リフローの基準。いちばん崩れやすい）、1920（行が長くなりすぎないか）。

#### 幅を合わせる（親がやる）

1. `resize_window` でウィンドウの大きさを変える
2. `javascript_tool` で `window.innerWidth` を測る。ウィンドウの枠のぶんずれるので、差を足してもう一度変える
3. Chrome にはウィンドウの最小の幅があり、375px まで縮まないことがある。そのときは **ブラウザの拡大で合わせる**: ウィンドウを 750px にして 200%（`computer` で Ctrl+=、Mac は Cmd+=）にすると、中身の幅は 375 CSS px になる（WCAG のリフローの確かめ方と同じ）。拡大はホストごとに全タブにかかる
4. 測った `innerWidth` を記録し、サブエージェントに渡す。合わせられなかったら、実際に測った幅で点検したと書く（「375px で確かめた」と偽らない）

#### サブエージェントに配る

- 画面を3〜4組に分け、`general-purpose` のサブエージェントを **1つのメッセージで同時に** 起動する（`references/agent-prompt.md` のひな形に、URL・幅・本番かどうかを埋める）
- サブエージェントは、自分で開いたタブだけを使い、**ウィンドウの大きさと拡大率を変えない**。終わったら自分のタブを閉じる
- UX と OOUI の点検（操作の流れ）は、PC の幅のときに1つのサブエージェントへ別に渡す（例: ページを探して開く、新しいページを作る、予約する、wiki を切り替える）。本番では、流れの途中の保存の手前で止める
- サブエージェントが Chrome の道具を使えない、またはタブのスクリーンショットが別のタブのものになるなど、並行がうまくいかないときは、並行をやめて自分で順に点検する

全部の幅が終わったら、拡大を 100% に戻し（Ctrl+0）、ウィンドウの大きさを元に戻す。

### 5. まとめる

サブエージェントの結果を集めて、次の順に整理する。

1. **同じ原因はまとめる**: 同じコンポーネントの崩れが複数の画面・幅で出ていれば1件にし、出る画面と幅を並べる
2. **コードの場所を当てる**: 画面の文言やクラス名から `grep` し、直すファイルとコンポーネントを特定する（issue に書くため）
3. **重大度を付ける**（`references/checklist.md` の「重大度」）。重大度1（見た目だけ）は画面ごとに1件へまとめる
4. **すでにある issue を探す**: `mcp__github__search_issues`（`repo:itizawa/wiki is:open`）で、同じ内容が無いか確かめる。あれば新しく作らず、一覧にその番号を書く
5. **思い込みを外す**: 「わざとそうしている」かもしれないもの（README に理由が書いてある挙動など）は README を見て確かめ、仕様なら落とす

### 6. ユーザーに確かめてから起票する

まとめた一覧を、重大度の高い順に表で見せる（タイトル、重大度、画面、幅、既存の issue）。そのうえで `AskUserQuestion` で聞く。

- 全部起票する（おすすめ）
- 重大度3以上だけ起票する
- 起票しない（一覧だけ欲しい）

「Other」で番号を選んでもらってもよい。

### 7. issue を作る

`.claude/skills/create-issue/SKILL.md` の「本文の形」と「書き方」に従う。加えて、次を入れる。

- **タイトル**: 何を直すかが一行でわかるように（例: 「スマホ幅でページ一覧の表が横にはみ出すのを直す」）
- **現状** に、再現の手順をそのまま書く
  - URL（本番か手元か）、点検した中身の幅（`innerWidth`。拡大で合わせたならそれも）
  - 何をしたら、何がどうなるか。期待していた見え方
  - `layout-probe.js` で測った数字（はみ出した要素とその幅、押せる部分の大きさなど）
  - コンソールのエラーがあれば、その文
- **重大度** と、どの観点か（例: 「重大度 3・表示崩れ（横のはみ出し）」「重大度 2・UX（操作の結果がわからない）」「重大度 2・OOUI（一覧が主役になっていない）」）を「やりたいこと」の最後に書く
- 「確認すること」に、直したあとに見る幅（例: 320 / 375 / 768 / 1280）と、CLAUDE.md の「UI を変えたら PR にスクリーンショットを載せる」を入れる
- スクリーンショットは API で issue に貼れない。貼ったふりをせず、手順と数字で再現できるように書く

作るのは `mcp__github__issue_write`（`method: "create"`、`owner: "itizawa"`、`repo: "wiki"`）。1回の点検で作るのは多くても10件にし、残りは一覧のまま渡す。

### 8. 伝える

作った issue の URL を重大度の順に並べ、次も書く。

- 点検した画面と幅（合わせられなかった幅があればそれも）
- 起票しなかったもの（既存の issue と同じ、仕様だった、件数の上限で残した）
- 見ていないこと（ダークモードは OS の設定に従うので、OS を切り替えないと見られない。実機のタッチ・ソフトウェアキーボード・iOS の Safari は Chrome では再現できない）

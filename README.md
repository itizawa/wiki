# wiki

書いたそばから流れていく公開型wiki。wiki を複数持て、1つの wiki にツリーは1本。記事を公開まで運ぶワークフローを主役にする予定で、いまは書く・公開する・予約するところまでを実装している（定型のルールはいったん消した。下の「ルールについて」）。

## コンセプト

めざす姿：ネタをページとして置けば、下書き起こし・置き場所の提案・公開前チェック・予約枠への投入までをワークフローが進め、人は「書く」と「確かめる」に集中する。ワークフローはまだ無い。

- **wiki = ページ・ツリー（1本）・予約・設定のまとまり**。wiki は複数作れ、wiki どうしは内容を共有しない。それぞれ別のサブドメイン（`{key}.hatchery-works.com`）で公開する
- **1つの wiki にツリーは1本**。記事の置き場所を決めるためのもので、1つの wiki の中に複数ツリーや構造のブランチ/マージは持たない
- **ノードはすべてページ**。フォルダや Inbox は無く、ページの下にページを置いて階層を作る（GROWI などと同じ考え方）。まとめ役が欲しければ、それもページとして書く

### フェーズ3の進め方

| | 内容 | 状態 |
|---|---|---|
| 3a | ツリー1本化（複数ツリーとブランチの UI・API を外す） | 済 |
| 3b | ルールエンジン：記事の状態、定型ルール3つ、実行ログ | いったん消した（下の「ルールについて」） |
| 3c | AI アクション：下書き、公開前チェック、置き場所の提案 | 未着手（ワークフローを作り直してから） |

## 構成

```
apps/admin       管理画面（React + TanStack Router/Query + dnd-kit、Vite）
apps/api         API（Hono + Drizzle + PostgreSQL）
apps/worker      Cron Triggers：下書きを版にする・予約公開の実行・公開ビルドの起動、1日1回の間引きと掃除（版、役目を終えたトークンと公開イベント、週1回は参照されていない画像）
apps/site        公開サイト（Astro + Reactアイランド、Pagefind、Cloudflare Workers の静的アセット）
packages/shared  型、zodスキーマ（構造操作）、URLルール、構造の適用・検証・差分
```

## wiki（複数の wiki）

- **key**：公開サイトのサブドメインになる名前。半角の英小文字・数字・ハイフン、3〜32文字、先頭は英字、末尾はハイフン以外。`wiki-admin` `www` `api` など、使用中・紛らわしい名前は使えない（`packages/shared/src/wiki.ts` の `RESERVED_WIKI_KEYS`）。**作成後は変えられない**（公開 URL がすべて変わるため）。表示名（`name`）はあとから変えられ、公開サイトの名前になる
- 最初の wiki は `key = wiki`（`wiki.hatchery-works.com`）。wiki が1つだった頃の内容は、すべてここにある
- **作成・名前の変更・アーカイブ・戻す**は、管理画面の「全体の管理」の「wiki」タブ（`/wikis`）から、オーナーだけが行える（「ユーザーとロール」）
  - 「全体の管理」は、wiki をまたぐオーナー向けの4画面（wiki `/wikis`・オーナー `/owners`・すべての wiki の監査ログ `/audit`・コスト `/costs`。下の「運用コスト」）をタブでまとめた画面。サイドバーには出さず、入口はサイドバーの上の wiki の切り替えメニューの「全体の管理」（オーナーにだけ出す）
  - 作った wiki には空のツリーを1本用意する。作ったオーナーは、その wiki の管理者としてメンバーに入る
  - 削除は**アーカイブ**（完全な削除は無い）。公開サイトは次のビルドで止まり（そのサブドメインは 404）、管理画面の一覧から外れ、予約は実行されなくなる。データは残り、オーナーが元に戻せる。アーカイブ中も、その key はほかの wiki で使えない
  - 元に戻しても、止まっていた間に時刻を過ぎた予約は実行せず、失敗として編集カレンダーに出す
  - **公開サイトだけを閉じる**（`wikis.site_public`、既定は公開）。「設定」の「一般」タブで、オーナーだけが切り替える（API は `PATCH /admin/w/{key}/settings` の `sitePublic`。ほかのロールは 403）。非公開の間は、アーカイブ中と同じようにマニフェストから外れ、次のビルドでそのサブドメインは 404 になる（トップ・`/p/{id}`・`/u/...`・`feed.xml`・`sitemap.xml`・検索のどれも見られない）。各ページの公開範囲（`visibility`）は触らないので、公開に戻せば元のとおりに出る。管理画面・MCP・予約の実行は今までどおり動き、管理画面の一覧からも外れない（アーカイブとの違い）。画像（`/images/{name}`）は URL を知っていれば見られる決まりのまま。値が実際に変わったときだけ `publish_events`（`wiki_site_visibility`）に記録してビルドし直し、監査ログ（`wiki_site_visibility`、「公開」の区分）に残す。ページの公開メニューには、サイトが非公開のときに「まだだれにも見えない」と出す（公開は止めない）
  - 最初の wiki もアーカイブできる。使用中の wiki が無くなると、管理画面は「wiki を作成する」だけを出す
- **管理画面は1つ**（`wiki-admin.hatchery-works.com`）で、URL に wiki が入る（`/w/{key}/...`）。サイドバーの上で wiki を切り替える。`/` は最後に開いていた wiki へ移る
- **wiki のトップ**（`/w/{key}`）は「ダッシュボード」：閲覧数（Google Analytics の直近28日間の要約。詳しい数字は「アクセス解析」）、最近更新したページ・下書き（まだ一度も公開していないページ。`GET /pages?published=false`）・予約公開の一覧を、各6件まで出す。全ページの一覧は `/w/{key}/pages`（サイドバーの「すべてのページ」）
- **wiki ごとの設定**は、サイドバーの「設定」（`/w/{key}/settings`）に、タブでまとめている。タブごとに URL が分かれ、再読み込みや URL の共有で同じタブが開く
  | タブ | URL | 中身 | 出す人 |
  |---|---|---|---|
  | 一般 | `/w/{key}/settings` | wiki の表示名と画像、key と公開サイトの URL（変えられない） | だれでも（変えるのはオーナーだけ） |
  | 外観 | `/w/{key}/settings/appearance` | 公開サイトの外観（下の「公開サイトの外観（テーマ）」） | 管理者だけ |
  | トップページ | `/w/{key}/settings/home` | 公開サイトのトップの自由記述（下の「公開サイトのトップページ」） | 管理者だけ |
  | 連携 | `/w/{key}/settings/integrations` | Google Analytics・サーチコンソール | だれでも（変えるのはオーナーだけ） |
  | SNS | `/w/{key}/settings/sns` | X のアカウントとの連携（下の「SNS 連携」） | 管理者だけ |
  | メンバー | `/w/{key}/settings/members` | メンバーと招待（「ユーザーとロール」） | だれでも（変えるのは管理者だけ） |
  | 監査ログ | `/w/{key}/settings/audit` | この wiki の監査ログ（「監査ログ」） | 管理者だけ |
  - タブにまとめる前の URL（`/w/{key}/members` `/audit` `/appearance` `/home`）は、新しいタブへ移す
- **API** は wiki を経路で受け取る（`/admin/w/{key}/pages` など）。リクエストのたびに wiki と、ログインしている人のその wiki でのロールを引き（メンバーでない wiki は 404）、すべての問い合わせを `wiki_id` で絞る。ページの ID だけを指定する経路でも、そのページが指定の wiki のものかを確かめる（別の wiki のページ ID は 404）
- wiki をまたぐもの
  - ページを別の wiki へ移す操作は無い。ページの ID は全体で重ならない
  - 別の wiki のページへのリンクは外部リンクと同じ扱い（`page_links` に残さず、公開サイトでも内部リンクにしない）
  - 検索・新着・RSS・サイトマップ・Pagefind の索引、管理画面の検索・編集カレンダーは、wiki ごと
  - 通知先（`NOTIFY_WEBHOOK_URL`）は全体で1つ。通知の文面に wiki の名前が入る
- **Google Analytics とサーチコンソール**は wiki ごとに設定する（GA のデータストリームも、サーチコンソールのプロパティも wiki ごと）。管理画面の「設定」の「連携」タブ（`/w/{key}/settings/integrations`）に、GA4 の測定 ID（`G-` で始まる）と、サーチコンソールの確認用の値（「HTML タグ」の `content` の値。タグごと貼ってもよい）を入れて保存すると、数分後のビルドで、その wiki の公開サイトの `<head>` に Google タグと `<meta name="google-site-verification">` が入る。空にして保存すると外れる
  - 読むのはその wiki を開ける人の全員、変えるのはオーナーだけ（`GET` / `PATCH /admin/w/{key}/settings`）。値が実際に変わったときだけビルドし直す
  - **限定公開のページ（`/u/{key}/`）には、どちらのタグも出さない**（Google へ限定公開の URL を送らないため）。404 のページには出すが、開いている URL が `/u/` で始まるとき（無くなった限定公開の URL）は、Google タグを読み込まない。`build:sample` の検査で確かめる
  - 値は公開サイトの HTML にそのまま出るので、決まった形のものだけを通す（測定 ID は `G-` + 英大文字と数字4〜20文字、確認用の値は英数字と `-` `_` で100文字まで。`packages/shared/src/wiki.ts`）。`UA-`・`GTM-`・`AW-` は使えない。API は形の合わない値を 400 にし、公開サイトのビルドも形の合わない値は出さない
  - Cookie の同意バナーは無い。GA は閲覧者のブラウザに Cookie を置く
  - つないだあとの数字は、管理画面の「アクセス解析」で見られる（下の「アクセス解析」）。同じ「設定」に、GA の**プロパティ ID**（数字だけ。測定 ID とは別の番号）を入れる。プロパティ ID は管理画面だけが使い、公開サイトには出さず、変えてもビルドし直さない
- **公開サイト**は Worker もビルドも1つ。1回のビルドで全 wiki のぶんを wiki ごとのディレクトリに出力し、Worker が `Host` を見てその wiki のディレクトリから返す（`apps/site/README.md`）。どれか1つの wiki の内容が変わると全体をビルドし直す。公開用のデータ（`/export/public`）には、全体の `contentHash` のほかに wiki ごとの `contentHash` も入れてある（変わった wiki だけを作り直すための準備。いまのビルドは使っていない）
- データ：`wikis`（`id` / `key` / `name` / `archived_at` / `created_at` / `created_by`（作ったオーナーのメールアドレス））。`pages` `trees` `scheduled_actions` `publish_events` が `wiki_id` を持つ

## リンクカードと「@タイトル」

- **外部の URL だけの段落**（`https://…` だけの行。専用の記法は無い。判定は `packages/shared/src/linkCard.ts`）は、管理画面と公開サイトでカード（サイト名・タイトル・説明、管理画面は右に小さな画像）で出す。文章の中のリンク・`[文字](URL)`・URL のあとに文字が続く行・Google マップの URL は、これまでどおり
  - 管理画面：空の段落に URL を貼ると、API から OGP を取ってカードにする（取る間と、取れなかったときは URL の行のまま）。カードを選ぶ（Tab でも）と「リンクをコピー」と「リンクに戻す」が出る。戻すと `[URL](URL)` のリンクの段落になる。Ctrl/Cmd + Z で貼る前に戻る
  - OGP は `GET /admin/w/{key}/link-preview?url=…`（wiki のメンバーだけ。人ごとに60秒で30回）。API が代わりに取り、`link_previews` に保存する（取れたものは7日、取れなかったものは1時間は取り直さない）。取りにいく先は https・443・ドメイン名だけ（IP の直書き・`localhost`・内部のドメインは断る）、リダイレクトは3回まで（先にも同じ確かめをする）、応答は1MB・3秒まで、`text/html` だけ（`apps/api/src/linkPreview/`）。画像は URL だけを持ち、ファイルは保存しない
  - 公開サイト：ビルドが `/export/public` を読むとき、API が URL だけの段落の OGP を取って保存し（1回に30件まで）、マニフェストの `linkPreviews` に入れる。ビルドは外へ取りにいかない。取れなかった URL は、ふつうのリンクで出す。カードは、スクリプトが無くても読めるただの `<a>`（新しいタブ、`rel="noopener"`）。**外部の画像は出さない**（読者のブラウザが外部のサイトへ読みにいくと、読者の IP が伝わるため）。`linkPreviews` は `contentHash` に入れない（公開したあとの最初のビルドで入る）
- **自分の wiki のページへのリンク**は、カードにしない。管理画面でそのページの URL を貼ると `[タイトル](/p/{id})` のリンクになる。リンクの文字がページの「いまのタイトル」そのままのものは、太字の「@タイトル」の見た目で出す（管理画面・公開サイトとも、CSS（`.page-mention`）だけ。本文の Markdown に `@` や `**` は書かない）。公開サイトで非公開のページへのリンクは、これまでどおり文字だけ（`@` も付けない）。文字を自分で変えたリンク（`[詳しくはこちら](/p/…)`）と、タイトルを変えたあとの古い文字のリンクは、ふつうのリンクのまま

## ユーザーとロール

管理画面に入れるのは、招待された人だけ。公開サイトは誰でも読める。

- ログインは **Google 認証**（OIDC、scope は `openid email profile`）。ユーザーは Google のアカウント ID（`sub`）で見分け、メールアドレスと名前は表示用にログインのたびに更新する。メールアドレスが未確認のアカウントはログインも参加もできない
- **メンバーは wiki ごと**。ロールは2つ
  | できること | 編集者 | 管理者 |
  |---|---|---|
  | ページの作成・編集・移動・削除（ゴミ箱から戻す・完全に削除するを含む）、公開・非公開化・公開範囲の変更・予約 | ○ | ○ |
  | 招待リンクの発行、メンバーのロール変更・削除 | — | ○ |
  | 公開サイトの外観（サイト名・アクセント色・ロゴ・ファビコン） | — | ○ |
  | 公開サイトのトップページの自由記述 | — | ○ |
  | SNS（X）のアカウントの連携・解除・テスト投稿 | — | ○ |
- **オーナー**は wiki のロールとは別の、全体の権限。すべての wiki に管理者として入れ（メンバーの一覧には出ない）、wiki の作成・アーカイブと、オーナーの追加・解除（管理画面の「全体の管理」の「オーナー」タブ、`/owners`）ができる。オーナーにできるのは登録済みのユーザーで、最後のオーナーは解除できない
- 権限は API で確かめる。管理画面は、できない操作のボタンを出さない
- **招待**：管理者が、ロールを選んで招待リンクを発行する（「設定」の「メンバー」タブ）。1リンクで1人、期限は7日、使われる前なら無効にできる。リンクは発行した直後に一度だけ見せ、DB には SHA-256 のハッシュだけを持つ（値は 128bit の乱数）。メールは送らない
  - リンク（`/invite#{token}`）を開くと wiki の名前・ロール・期限を出す。ログインしていなければ「Google でログインする」でログインし、招待の画面に戻ってから「参加する」を押す（リンクを踏ませただけで知らない wiki に入らないように、ログインのあとすぐには参加させない。ログインをまたいで、招待を OAuth の state と同じ短命の署名付き Cookie で引き継ぐ）
  - リンクの値は、サーバーへのリクエストの URL に載せない（アクセスログに残さない）。リンクはフラグメント（`#` のあと）に置き、API にはリクエストの本文で送る（`POST /api/invites/inspect`・`/accept`、ログインはフォームの POST）
  - **管理者でなくなった人が発行した招待は使えない**。メンバーから外す・編集者にする・オーナーを解除する（メンバーの管理者として入っていない wiki の分）ときに、その人が発行した使われる前の招待を同じトランザクションで無効にする。受けるときにも、発行した人がいまもその wiki の管理者（オーナーを含む）かを確かめる
  - すでにその wiki のメンバーなら、リンクは使わずに残す（ロールも変えない）。期限切れ・使用済み・無効なら、理由と「管理者に新しいリンクを頼んでください」を出す
  - 同じリンクを2人が同時に使っても、使用済みにできた1人だけが入れる
- **メンバーの管理**：管理者はロールを変え、メンバーを外せる。自分から抜けることもできる。**メンバーの管理者が0人になる操作は止める**（オーナーは数えない）。外した人は次のリクエストからその wiki を開けない。外した人の行と、その人が書いた版・履歴は残す
- どの wiki のメンバーでもなく、オーナーでもない人は、Google でログインできても中に入れない（「この管理画面は招待制です」）。このときユーザーの行は作らない
- **セッション**は署名付き Cookie にユーザーの ID と、端末ごとのセッションの行（`sessions`）の ID だけを入れ、リクエストのたびに DB でセッションの行・ユーザー・wiki のメンバーかを確かめる。期限は7日
  - Cookie の名前は、https では `__Host-wiki_session`（OAuth の state を運ぶ一時の Cookie は `__Host-wiki_oauth`）。`__Host-` を付けた Cookie は、ブラウザが `Secure`・`Path=/`・`Domain` なしのものしか受け付けないので、同じドメインの兄弟である公開サイト（`{key}.hatchery-works.com`）から同じ名前の Cookie を植えられない。http の手元の開発では `__Host-` が使えないので、`wiki_session`・`wiki_oauth` のまま
  - `__Host-` を付ける前の名前（`wiki_session`・`wiki_oauth`）の Cookie が https で送られてきたら、読み取らずに消す
  - **ログアウト**すると、その端末のセッションの行を消す。Cookie の値が漏れていても、次のリクエストから通らない。ほかの端末はログインしたまま
  - 左下のユーザーメニューの「**ほかの端末からログアウトする**」で、この端末のほかのセッションをすべて切れる（Cookie が漏れたかもしれないとき・共用の端末でログアウトし忘れたとき）
  - 期限切れの行は通さず、その人が次にログインしたときに消す
- データ：`users`（`id` / `google_sub` / `email` / `name` / `is_owner` / `created_at` / `last_login_at`）、`sessions`（`id` / `user_id` / `created_at` / `expires_at`）、`wiki_members`（`wiki_id` / `user_id` / `role` / `created_at` / `invite_id`）、`invites`（`id` / `wiki_id` / `role` / `token_hash` / `created_by` / `expires_at` / `used_by` / `used_at` / `revoked_at`）
- **締め出されたとき**（オーナー全員がログインできなくなった等）は、DB に直接つないでオーナーを付ける：`DATABASE_URL=... pnpm db:grant-owner you@example.com`。同じメールアドレスのユーザーがいればオーナーにし、いなければメールアドレスだけの行を作る（最初の Google ログインで結びつく）
  - **メールアドレスだけの行は、そのアドレスで最初にログインした Google アカウント（メールアドレスが確認済みのもの）に結びつく**。`ADMIN_EMAILS` の移行・`db:grant-owner`・スターと下書きの移行が作る行がこれにあたる。会社の Google Workspace のアドレスなら持ち主は1人だが、Gmail 以外の個人のアドレスなどは、同じアドレスを確認した別の Google アカウントがありうる（使われなくなったアドレスの再割り当てなど）。使うのは自分が持っているアドレスだけにし、「全体の管理」の「オーナー」タブで「まだログインしていません」の行が残っていないか確かめる

## 監査ログ

「誰が・いつ・何をしたか」を、あとから確かめるための記録。管理画面の「監査ログ」で見る。

- **2つに分けて残す**
  - 本文の保存は、版履歴に「誰が」を足して残す（`page_versions.created_by`）。監査ログには入れない（件数が多く、版履歴の画面で追えるため）。版履歴の画面に名前を出す。自動でできた版には、もとの下書きを書いていた人が入る。これより前の版と、システムによるものは空。並べ替え・移動・ページの作成は、どこにも記録しない
  - 次の重要な操作は、監査ログ（`audit_logs`）に残す
- **残る操作**（操作の種類の一覧は `packages/shared/src/audit.ts` の `AUDIT_ACTIONS`）
  | 分類 | 操作 |
  |---|---|
  | ログイン | ログイン、ログインの拒否（招待されていない・メールアドレスが未確認）、ログアウト |
  | メンバー | 招待リンクの発行・使用・無効化、ロールの変更、メンバーの削除、自分で抜けた、オーナーの追加・解除 |
  | 公開 | 公開（公開し直しを含む）、非公開化、公開範囲の変更、限定公開 URL の再発行、予約の作成・日時の変更・取り消し、予約の実行（成功・最終的な失敗。再試行に戻したものは残さない）、公開サイトの公開・非公開化 |
  | ページ | 削除（ゴミ箱に入れる）、ゴミ箱から元に戻す、ゴミ箱から完全に削除する |
  | 設定 | wiki の名前・画像の変更、公開サイトのトップページの自由記述の変更（中身は残さない）、SNS（X）のアカウントの連携・解除・テスト投稿（文面とトークンは残さない）、Routine の登録・変更・削除・テスト実行（トークンは残さない。全体にかかわるものとして wiki なし） |
  | wiki | 作成、アーカイブ、元に戻す |
- **残らない操作**：本文の保存・下書きの自動保存、ページの作成・並べ替え・移動（記録しない）、下書きから自動で版ができたこと、アイコンの変更、wiki の設定（Google Analytics・サーチコンソール）の変更、公開サイトの外観（テーマ）の変更、スター、テンプレートの作成・変更、画像のアップロード、管理画面でページを開いたこと（閲覧）。アーカイブから戻したときに、止まっていた間に時刻を過ぎた予約を失敗にすること
- **1件に持つもの**：いつ、どの wiki で（ログイン・オーナーの変更・wiki の作成とアーカイブは、全体にかかわるものとして wiki なし）、誰が（ユーザー／システム（予約の実行））、何を（操作の種類・対象）、変更の前と後（`detail`）
  - 予約の実行には、その予約を入れた人も残す
  - 人の名前・メールアドレスと、対象のタイトルは、その時点の値を写して持つ（あとで名前が変わっても、ページが消えても読める）
  - **本文、招待リンクや限定公開 URL の値、シークレットは入れない**
  - IP アドレスと User-Agent は、ログイン・ログインの拒否のときだけ残す（`cf-connecting-ip`、無ければ `x-forwarded-for` の先頭）
- **書き込み**：操作と同じトランザクションで書き、書けなければ操作も失敗させる（記録の無い操作を作らない）。ログインの拒否やログアウトのように、もとの操作にトランザクションが無いものは単独で書く
- **追記だけ**。直す・消す API は無い。期限で消す仕組みも無く、増えてきたら改めて決める。書き出し（CSV など）と外への転送も、いまは無い
- **見られる人**：wiki の管理者は、その wiki の記録（「設定」の「監査ログ」タブ、`/w/{key}/settings/audit`）。オーナーは、すべての wiki と全体にかかわる記録（「全体の管理」の「監査ログ」タブ、`/audit`）。編集者には出さない
  - 新しい順で、続きは「続きを読み込む」で読む。期間・人・分類（オーナーは wiki も）で絞り込める
- `publish_events`（ビルドを起動するため）は役割が違うので、そのまま残している
- データ：`audit_logs`（`id` / `wiki_id` / `actor_type` / `actor_user_id` / `actor_label` / `actor_email` / `via` / `action` / `target_type` / `target_id` / `target_label` / `detail` / `ip` / `user_agent` / `created_at`）、`scheduled_actions.created_by`（予約を入れた人）

## フェーズ1で入っているもの

- Google認証（OIDC）。セッションは署名付きCookie（「ユーザーとロール」）
- `pages` / `page_versions`：Markdownエディタ、版履歴と差分、楽観ロック（`base_version_id` が head と一致する場合のみ保存）
- `page_drafts`：編集中の内容は、打つのが止まると（1.5 秒）人ごとの下書きとして自動保存する。ページと人ごとに1行で、上書きする
  - 編集が一段落したら、ワーカーが下書きを版にして、下書きを消す（`/internal/tick`、5分ごと）。一段落したとみなすのは、最後の自動保存から5分たったとき。打ち続けているあいだも、下書きを始めてから30分たてば版にする（時間は `apps/api/src/pages/versions.ts` の定数）。版になるまでは、5分＋ワーカーの間隔（最大5分）で、5〜10分
  - 版にしない下書き：タイトルが空のもの、古い版をもとにしたもの（あいだにできた版の変更を黙って上書きしないため）、削除したページやアーカイブ中の wiki のもの。消さずに残す
- 管理画面の検索（検索の画面、コマンドメニュー（⌘K）、本文の「@」「[[」のリンクの挿入。`GET /search`）：開いている wiki の、タイトルといまの本文（head 版）を `ILIKE '%語%'` で探す
  - 探す先は `page_search`（head 版のタイトルと本文の写し。ページごとに1行）。**head 版を進める所は、同じトランザクションで `syncPageSearch`（`apps/api/src/pages/versions.ts`）を呼ぶ**。いまは `createPage` と `createVersion` が呼んでいて、保存・下書きから版になるとき・前の版の内容での保存・MCP の `update_page` は、どれも `createVersion` を通る。完全に削除したページの行は消す
  - 索引は pg_trgm の GIN（`page_search_title_trgm_idx` `page_search_body_trgm_idx`）。3文字以上の語で効く。1〜2文字の語は trigram が取れないので、`page_search` を全部読んで探す（結果は同じ）
  - 語が空のとき（候補の一覧の初期表示）は、本文を読まず、`pages` から最近更新した50件を返す
  - 管理画面は、打つのを止めてから 200ms たって探しにいく。日本語入力などの変換中は探さず、確定してから数える。語を空にしたときは待たない（`apps/admin/src/lib/searchTerm.ts` の `useSearchTerm`。3つの画面が同じものを使う）
  - MCP の `search_pages` は別の検索で（エージェントが読める版を探す）、索引を使わない
  - 区切りたいときは、⌘S・編集画面の「…」メニュー・コマンドメニューの「いまの内容を版として残す」で、すぐ版を作れる。公開・予約を押したときも、版になっていない変更があれば先に版を作る。公開・予約は版に対して行う
  - 版には、間引かずに残すかどうかの印（`page_versions.keep`）がある。ワーカーが作った版は `false`（版履歴に「自動」と出る）、人が操作して作った版と、公開・予約に使った版は `true`
  - 自動でできた版（`keep = false`）は、古いほど粗く間引く（`/internal/versions/prune`、1日1回、JST の午前3時。`apps/api/src/pages/prune.ts`）。**消した版は戻せない**
    - できてから24時間以内の版は、すべて残す。30日以内は JST の1日に1つ、それより前は JST の1か月に1つ（その区切りでいちばん新しい自動の版）を残し、残りを消す。時間（24時間・30日）は API の定数
    - 消さない版：残す版（`keep = true`。⌘S などで人が作った版、公開・予約に使った版）。自動の版でも、どれかのページの最新の版・公開中の版、予約が指す版（終わった予約・取り消した予約も含む）、下書きがもとにしている版、編集リクエストの項目が基準にしている版、外部のアプリ（MCP）が保存した版の派生元
    - 残す版は数に入れない。同じ日に残す版があっても、自動の版のうちいちばん新しい1つは残る
    - 消した版を派生元（`base_version_id`）にしていた版は、派生元が null になる
    - 1回に消すのは1000件まで（残りは次の日）。ゴミ箱のページやアーカイブ中の wiki の版も、同じ決まりで間引く（最新の版は残るので、元に戻せる）
- 画像のアップロード：本文への貼り付け・ドラッグ、挿入メニューの「画像…」から。PNG・JPEG・WebP・GIF、5MB まで（形式は中身で判定し、SVG は受け付けない）
  - 大きさは API が本文を読みながら数え、上限を超えた所で読むのをやめて 413 を返す（大きさを申告しない送り方でも、全体をメモリに載せない）。ロゴとファビコンのアップロードも同じ
  - wiki の画像（「全体の管理」の「wiki」タブの「表示名と画像」）も、同じ仕組みでアップロードできる（ファイルの選択か、枠へのドラッグ）。管理画面で画像を1枚アップロードする部品は `apps/admin/src/components/ImageUploader.tsx`
  - 置き場所は Cloudflare R2 のバケット `wiki-images`。名前はランダムな24文字で、本文には相対パス `/images/{name}` と書く。管理画面（`wiki-admin`）と公開サイト（`wiki-site`、どの wiki のサブドメインでも）が、同じバケットからこのパスで配る
  - 認証はしない。非公開・限定公開のページに貼った画像も、URL を知っていればだれでも見られる
  - 名前が同じなら中身も同じなので、ブラウザに1年キャッシュさせ（`immutable`）、Cloudflare のエッジのキャッシュ（`caches.default`）にも入れる。2回目からは、初めて来るブラウザにも R2 を読まずに返す（管理画面は `apps/api/src/worker.ts`、公開サイトは `apps/site/worker/index.ts`）。キーは URL（クエリを除く）で、入れるのは見つかった画像だけ。R2 から画像を手で消しても、キャッシュに残っている間は返り続ける
  - 手元の開発（`pnpm dev`）では `apps/api/.data/images`（`IMAGES_DIR` で変えられる）に置く
  - どこからも参照されていない画像は、週1回消す（`/internal/versions/prune` に `{"images": true}` を渡した回。ワーカーが日曜 18:00 UTC = JST の月曜午前3時に渡す。`apps/api/src/images/cleanup.ts`）。**消した画像は戻せない**
    - 消すのは、次のどこにも `/images/{name}` が書かれておらず、アップロードから30日より古い画像：すべての版の本文（ゴミ箱のページ・アーカイブ中の wiki の版も含む）、下書き、テンプレート、トップページの自由記述、wiki の画像、テーマのロゴとファビコン、ページのカバー画像
    - ゴミ箱から完全に削除したページは版ごと消えるので、そのページだけが使っていた画像は、アップロードから30日たっていれば次の回で消える。ロゴや wiki の画像を差し替えたときの前の画像も同じ
    - アップロードから30日以内の画像は、参照が無くても消さない（貼ったばかりで、まだ保存されていない画像を消さないため）。名前がアップロードした画像の形でないものにも触らない
    - 1回に消すのは1000枚まで（残りは次の週）、一覧から読むのは20,000枚まで。消す前に、件数を API のログに出す（`imageCleanup`）。読む上限に当たると `truncated: true` になる。名前の順で後ろの画像を見られなくなるので、そのときは上限（`IMAGE_CLEANUP_MAX_LISTED`）を上げる
    - **画像のパスを書ける列を足したら、`referencedImageNames` にも足す**（足し忘れると、そこでだけ使っている画像が消える）
- 役目を終えた行の掃除（版の間引きと同じ `/internal/versions/prune`、1日1回）。**消した行は戻せない**。1回に消すのは、表ごとに5000行まで（残りは次の日）
  - `oauth_tokens`・`oauth_codes`（`apps/api/src/oauth/cleanup.ts`）：期限を7日より前に過ぎた行のうち、アクセストークン、使われなかった認可コード、取り消し済みか期限切れの許可のリフレッシュトークンと認可コード
    - 使える許可の、入れ替え済みのリフレッシュトークンと使った認可コードは残す。もう一度使われたら漏れたものとみなして許可ごと取り消すので、行が無いと検知できなくなる。許可は90日で切れるので、残るのは許可1つにつき90日ぶんまで
    - 許可（`oauth_grants`）とアプリ（`oauth_clients`）は消さない
  - `publish_events`・`site_builds`（`apps/api/src/publishing/cleanup.ts`）：30日より古い行のうち、ビルドに反映済みのイベントと、起動済みのビルド
    - 消さない行：いちばん新しい `site_builds`（どこまで反映したかを持つ）、起動済みのいちばん新しい `site_builds`（内容が変わったかを比べる相手）、起動できていない `site_builds`、まだ反映していない `publish_events`
  - `audit_logs` は、残す期間が決まっていないので消さない
- 構造：`trees` / `tree_nodes`
  - ツリーは、いまの状態だけを `tree_nodes` に持つ。過去の状態（履歴・差分・巻き戻し）は残さない
  - ツリーを変える操作（`apps/api/src/structure/repo.ts` の `changeStructure`）は、wiki の行をロックして1つずつ順に行う。楽観ロックは無く、後から書いた操作が勝つ（操作はノード単位で検証するので、消えたページや不正な移動は 422）
  - 1つの wiki にツリーは1本（primary）だけを扱う。テーブルは複数ツリーを前提にした形のまま残してあり、API と UI からは作れない
  - ノードはすべてページで `node_id = page_id`（ツリー内で移動してもURLが変わらない）
- ツリーUI：サイドバーの「ドキュメント」で完結する。ドラッグで並び替え・別のページの下へ移動、行の「＋」でその下にページを作成。専用の整理画面は無い

## フェーズ2で入っているもの

- 公開範囲：`public`（`/p/{id}`）／`unlisted`（`/u/{unlisted_key}/`、noindex・no-referrer、検索/サイトマップ/RSS/ナビ/リンクから除外）／`private`
  - 公開 = `published_version_id` を進める操作。公開後の編集は「最新版で公開し直す」まで公開側に出ない
  - 限定公開URLの再発行（旧URLは次のビルドで404）
  - 親子の決まり（[GROWI の閲覧権限](https://docs.growi.org/ja/guide/features/authority.html)に従う）：公開範囲はページごとに持ち、**配下のページには、親と同じか、より狭い公開範囲しか設定できない**（広い順に 公開 > 限定公開 > 非公開）。親が非公開なら、その下のページは公開も限定公開もできない。最上位のページはどれでも選べる
    - 新しいページは、親に関係なく非公開（下書き）で作る。公開するのは今までどおり人の操作
    - 公開範囲を変えるときに「配下のすべてのページも同じ公開範囲にする」を選べる（1トランザクションで行い、ページごとに `publish_events` を記録）。変わるのは配下の公開中のページだけで、まだ公開していないページは公開する版が決まっていないので非公開のまま飛ばす。上書きしたあとは、それぞれのページで個別に変えられる
    - 配下に、選んだ公開範囲より広いページがあるときは、「配下も同じにする」を選ばない限り変えられない（非公開にする場合も同じ）
    - 移動先の親より広い公開範囲のページは移動できない（先に公開範囲を狭める）。ページをゴミ箱に入れる・元に戻すときは止めない（戻したページは非公開なので、親より広くならない）
    - 予約は、その時刻の公開範囲（それまでに実行される予約を含む）で確かめる。親の公開を先に予約してあれば、その後の子の公開も予約できる。同じ `batch_id` の中は、公開は親から、非公開化は子から実行する
    - 決まりを入れる前からある、決まりに合わないページ（非公開の親の下の公開ページなど）はそのまま残す。公開サイトは今までどおりページごとの `visibility` で出し、ツリーでは公開の祖先の下へ繰り上げる。そのページを次に変えるときから決まりを効かせる
    - 管理画面では、親の設定のために選べない公開範囲を選べない状態で見せ、理由を添える。サイドバーのツリーでは、限定公開（リンクの印）・非公開（鍵の印）のページに印を付ける
- 予約公開：`scheduled_actions`（公開・非公開化）。予約時点の版を固定し、予約後に編集があれば警告。同じ `batch_id` は1トランザクションで実行、失敗は3回まで再試行
- 公開パイプライン：操作ごとに `publish_events` を記録 → ワーカーがデバウンスしてビルド起動（`contentHash` が同じなら省略）→ サイトが `/export/public` を取得して静的出力 → Pagefind
  - 記録する操作（`publish_events.kind`）：公開・予約の実行（`publish`）、非公開化（`unpublish`）、限定公開URLの再発行（`rotate_unlisted_key`）、公開中のページのアイコンの変更（`icon`）、公開中のページのカバーの変更（`cover`）、公開したことのあるページをゴミ箱に入れる・元に戻す（`delete` `restore`）、並べ替え・移動（`structure`）、wiki の作成・設定の変更（`wiki_create` `wiki_rename` `wiki_theme` `wiki_home` `wiki_settings` `wiki_site_visibility` `wiki_archive` `wiki_unarchive`）
  - 並べ替え・移動（サイドバーのドラッグ、MCP の `move_page`）は、公開サイトのツリーに出るもの（公開中のページの親子と並び）が変わるときだけ記録する。非公開・限定公開のページだけを動かしたときは記録せず、ビルドも起動しない。非公開のページを動かしても、その下に公開中のページがあって公開サイトでの位置が変わるなら記録する。公開し直さなくても、次のビルドで公開サイトのツリーに出る
  - `contentHash` は、公開サイトの出力に出るものだけから作る（`apps/api/src/publishing/manifest.ts` の `wikiContentHash`）。wiki ごとに、key・名前・テーマ・トップの自由記述・Google Analytics とサーチコンソールの値、公開ページの id・公開版の ID・アイコン・カバー・初回の公開日時・収益化の設定、限定公開のページの key・公開版の ID・アイコン・カバー、公開ツリーの親子と並び、公開後に削除した記事の id。全体の `contentHash` は、wiki の key と wiki ごとの `contentHash` から作る（wiki の作成・アーカイブ・復元でも変わる）
  - 版の題名・本文・作成日時は作ったあと変わらないので、本文の代わりに公開版の ID を入れる。ビルドするか決めるとき（`requestBuild`）は本文を読まない。`/export/public` も同じ計算なので、同じ時点の2つの `contentHash` は必ず同じになる
  - 非公開のページは入れない。非公開のページの作成・並べ替えや、「公開してすぐ非公開に戻した」のように公開サイトに出るものが元に戻った操作では、ビルドしない
  - **公開サイトが使う項目をマニフェストに足したら、`wikiContentHash` にも入るようにする**（wiki の設定は、マニフェストに足せばそのまま入る。ページの項目は、題名・本文・改訂日だけを除いて入る）。入らないと、変えてもビルドが省かれる
- 公開サイト（`apps/site`）：記事（`/p/`。ツリーナビのリンクも `/p/` を指す）・新着一覧・検索（Pagefind、遅延ロード）・RSS・サイトマップ
  - 内部リンクは公開先の正規URLへ。非公開・限定公開・予約中のページへのリンクはテキストのみ
  - slug つきの旧URL（`/p/{id}-{slug}`）は `/p/{id}` へ 301（`apps/site/worker`）、削除記事は 410
  - ツリー経由の閲覧（`/t/{treeKey}/{nodeId}`）は廃止し、`/p/{nodeId}` へ 301（ツリーは1本なので、記事のページと同じものだった）
  - `monetization` が立った記事は「広告を含みます」を表示し、外部リンクに `rel="sponsored"`
- 管理画面：編集画面の右上の「公開」ボタンから開く枠（公開/非公開化/限定公開URL/予約。狭い画面では下から出るシート）、「…」メニューの「版履歴」から画面全体に重ねて開く版履歴（左に選んだ版との差分・本文、右に版の一覧。開いた版は `?history={版のID}` で URL に残る）、編集カレンダー（公開済み・予約・AI下書き、予約ストック警告、失敗一覧）

## ルールについて

フェーズ3b で入れた定型ルール3つ（承認済みの記事を予約枠に入れる・更新の無い記事を見直しキューに入れる・予約ストックが減ったら通知する）と、それに付いていた記事の状態（ネタ／下書き／承認済み）・見直しキュー・実行ログは、いったん消した（テーブルと列も落とした。マイグレーション `0018_remove_rules`）。柔軟に設定できるワークフローとして作り直す予定で、定型ルールはその土台にしない。

- ルールがすでに入れていた予約は、ふつうの公開予約として残り、予約の時刻に公開される
- 公開予約そのもの（「公開」の枠からの予約、編集カレンダー、予約ストックの警告、予約の最終失敗の通知）は変わらない

## 外部のアプリ（MCP）からの操作

Claude などの AI エージェントや手元のスクリプトから、MCP でページを探す・読む・書くことができる。許可すれば、公開・予約・削除もできる（例：検索ボリュームを元に記事を考えて書き、定期的に整理する）。認証は MCP の仕様にある OAuth 2.1 で、管理画面の Google ログインとは別の、短命のトークンを使う。

### つなぎ方

- MCP サーバーの URL は `https://wiki-admin.hatchery-works.com/mcp`（ローカルでは API のオリジンの `/mcp`）。管理画面の wiki の切り替えメニューにある「外部アプリ連携（MCP）」にも出る
- Claude：設定 → コネクタ → カスタムコネクタを追加 に URL を入れる。Claude Code：このリポジトリの中で起動すれば、`.mcp.json` に `wiki` として入っているのでそのまま使える（初回に、このサーバーを使うかを聞かれる。認可は `/mcp` から）。ほかの場所で使うなら `claude mcp add --transport http wiki https://wiki-admin.hatchery-works.com/mcp`
- つなぐと、ブラウザで管理画面の同意の画面（`/consent`）が開く。ログインして、許可することを選んで「許可する」を押す。許可したアプリの一覧と取り消しは「外部アプリ連携」の画面にある

  - 同意の画面では、`wiki.read` `wiki.write` `wiki.suggest` 以外は既定で外してある。アプリが依頼したものの中から、人が一つずつ選んで許す
  - `wiki.publish` を許したアプリは、人の確認を通さずに公開できる。外のアプリは許した人の代わりとして扱う
  - どのスコープでも、限定公開 URL の再発行・wiki の管理はできない
  - `wiki.private` が無いと、読めるのは公開中のページと、その許可で作ったページだけ。ほかのページは無いものとして扱い、ツリーではタイトルを伏せる。公開・削除もこの範囲のページだけ。ゴミ箱のページは非公開なので、一覧に出て元に戻せるのは、その許可で作ったページだけ
  - 公開中のページで読めるのは公開した版まで（公開前の書きかけは見せない）。書きかけがあるあいだは更新できず、公開・予約できるのも読める版だけ
  - 配下に読めないページがあると、移動・削除・元に戻す・配下をそろえる公開と非公開化はできない（非公開・限定公開のページの置き場所や公開範囲を変えないため）
  - `wiki.private` は同意の画面で既定では外してある。許すと、非公開の本文が外の AI サービスへ送られる
- どの許可（アプリ）からの操作かを残す（`page_versions` `publish_events` `scheduled_actions` の `oauth_grant_id`）。管理画面の版履歴に「〜 経由」と出る

### 認証のしくみ

- 認可サーバーは `wiki-admin` の Worker の中にある。メタデータは `/.well-known/oauth-authorization-server`（RFC 8414）と `/.well-known/oauth-protected-resource/mcp`（RFC 9728）。MCP サーバーはトークンが無いと `401` と `WWW-Authenticate: Bearer resource_metadata=...` を返し、クライアントはそこから認可サーバーを見つける
- アプリは動的クライアント登録（`/oauth/register`、RFC 7591）で登録する。秘密鍵を持たない公開クライアントだけで、**PKCE（S256）が必須**。戻り先（`redirect_uri`）は https か手元（`localhost` / `127.0.0.1` / `[::1]`）の http だけで、登録したものと完全一致でなければ戻さない。登録はログイン無しでできるので、許可が出ないまま1日たったものは消し、許可の無いものが200件を超えたら、古いものから消す（断らない。許可のあるものは消さない）
- 同意の画面には、アプリが名乗った名前と戻り先のホストを出す。依頼は署名して画面へ渡し（10分で切れる）、許すスコープは依頼の範囲から減らすことしかできない
- トークン
  - アクセストークンは1時間、リフレッシュトークンは30日。リフレッシュトークンは使うたびに入れ替え、入れ替え済みのものがまた使われたら、漏れたものとみなして許可ごと取り消す。認可コード（5分、1回だけ）の2回目の使用も同じ
  - 許可（同意）は90日で切れ、そのあとはつなぎ直して同意し直す
  - DB にはトークン・認可コードの SHA-256 ハッシュだけを持つ（`oauth_tokens` / `oauth_codes`）
  - リクエストのたびに、トークン・許可の取り消しと期限、許可した人が `ADMIN_EMAILS` にいるかを確かめる。取り消しや allowlist から外したことは、次のリクエストから効く
- アクセストークンは MCP サーバー（`/mcp`）でだけ使える。管理画面の API（`/admin/*`）は Cookie だけで、トークンでは通らない
- `/oauth/*` と `/mcp` は Cookie を見ないので、`Origin` の確認（CSRF 対策）の対象外。`/mcp` は、ブラウザからの呼び出し（`Origin` つき）を管理画面のオリジンからのものだけ受け付ける
- レート制限：許可ごとに1分あたり120リクエスト（`oauth_grants` の固定窓）。超えると `429`
- ログインせずに叩ける経路には、接続元（`cf-connecting-ip`）ごとの回数の制限もある（`apps/api/wrangler.toml` の `[[ratelimits]]`、`apps/api/src/rate-limit.ts`）。超えると `429` と `Retry-After` を返す（`/oauth/*` は OAuth のエラーの形で `temporarily_unavailable`）
  - `POST /oauth/register`：60秒で5回
  - `/oauth/authorize`・`/oauth/token`・`/oauth/revoke`：経路ごとに、60秒で30回
  - トークンの付いた `/mcp`：60秒で300回。トークンを DB で確かめる前に数えるので、正しいトークンのぶんも入る（許可ごとの120回より多くしてある）。トークンの無いリクエストは DB を引かずに `401` を返すので、数えない
  - 数えるのは Cloudflare の拠点ごとで、反映に少し遅れがある（厳密な上限ではなく、大量に叩かれたときの歯止め）。数えるのに失敗したときは通す
  - バインディングが無いとき（手元の `pnpm dev`、テスト）は制限しない
- データ：`oauth_clients`（登録したアプリ）、`oauth_grants`（同意。誰が・どのアプリに・どのスコープを・期限・取り消し・最後に使った日時）、`oauth_codes`、`oauth_tokens`

## 編集リクエスト

ページの本文に、箇所ごとの「こう直す」を提案してもらい、人が1件ずつ採用・却下を決める（GitHub の Suggestion にあたるもの）。直し方を示せないときは、置き換え案の無い指摘を箇所に付けられる。どの項目にも、返信を重ねられる。出せるのは、wiki のメンバー（レビュー画面の「編集リクエストを出す」）と、MCP でつないだ AI エージェント（`create_edit_request`）。採否は、wiki のメンバーならだれでも決められる。

- **形**
  - リクエスト（`edit_requests`）は、1ページに対する1回分。全体へのひとことと、箇所ごとの項目（`edit_request_items`）を持つ。リクエスト自体に状態は無く、未対応の項目が0件になったら終わり
  - 項目の位置は「基準の版（出したときの最新の版）・本文（Markdown）の行の範囲・その範囲の元の文面」。元の文面は、サーバーが基準の版から切り出す。出したあとの項目は書き換えられない
  - 項目は2種類（`kind`）。**提案**（`suggestion`）は置き換え案（`replacement_md`。空の文字は「その行を消す」）と、任意の理由を持つ。**指摘**（`note`）は置き換え案を持たず、本文（`note_body`。必須。プレーンテキスト）を持つ。種類ごとの形は、DB の制約（`edit_request_items_kind_shape_check`）でも守る
  - 項目の状態は、提案が 未対応（`open`）→ 採用（`accepted`）／却下（`rejected`）、指摘が 未対応（`open`）→ 解決済み（`resolved`）。どちらも取り下げ（`withdrawn`）にできる。却下と解決済みは、未対応に戻せる。取り下げは、出した本人（MCP からは、その許可で出したもの）だけ。種類に合わない操作は 409（指摘の採用・却下は `not_a_suggestion`、提案の解決済みは `not_a_note`）
  - **未対応は、種類を問わず `status = 'open'`**（`countOpenItems`、一覧の `openCount`、未対応だけの索引 `edit_request_items_open_idx`）。指摘も、解決済みにするまで未対応に数える。「すべて採用」は提案だけが対象で、指摘は未対応のまま残る
  - 指摘も、提案と同じく行の範囲と元の文面で位置を持ち、同じ決まりで「古くなった」になる。古くなった指摘も、解決済みにできる
  - **返信**（`edit_request_comments`）は、項目ごとに重ねる。本文はプレーンテキストで、画面では HTML としても Markdown としても描かない（改行は保つ。URL もリンクにしない）。項目の状態は問わず（採用・却下・解決済み・取り下げのあとも）書ける。書き換え・削除はできない。1つの項目に 200 件まで
  - 1回のリクエストは項目 50 件まで。置き換え案は 20,000 字、理由・ひとこと・指摘の本文・返信は 2,000 字まで（`EDIT_REQUEST_LIMITS`）
- **行の数え方**は1つだけ（`packages/shared/src/editRequest.ts` の `bodyLines`）。`body_md` を改行（`\n`）で区切り、1から数える。空行、表の行、コードブロックの中の行も1行。末尾が改行なら、最後に空の行が1つある。CRLF はそろえない。MCP の `get_page` が返す本文、サーバーが切り出す元の文面、管理画面の対応付けが、どれもこれで数える（版履歴の差分は、先頭に `# タイトル` と空行を足して比べているので、行番号が2つ大きい）
- **採用**
  - 最新の版の該当行を置き換えて、その場で新しい版を作る（`createVersion`。残す版で、作った人は採用した人）。公開はしない。公開中のページは、公開し直すまで公開側が変わらない
  - 最新の版が基準の版のままなら、行の範囲をそのまま置き換える。進んでいたら、元の文面を行のまとまりとして探し直し、1か所だけ見つかればそこを置き換える。見つからない・複数あるときは「古くなった」として採用できない（`applyLineEdits`）。古くなった項目は未対応のまま残り、却下・取り下げはできる
  - 「すべて採用」は、リクエストの未対応の項目のうち採用できるものだけを、1つの版にまとめる。行が重なる項目は、先に並んだほうだけ
  - そのページに、最新の版をもとにした下書き（編集中の人の自動保存）があれば、同じ置き換えを下書きにもかけ、もとにする版を新しい版に付け替える。下書きの側で元の文面が見つからなければ、採用を止めて、編集中の人の名前を返す（409 `draft_conflict`）
  - ページの行を `FOR UPDATE` で取ってから最新の版を読むので、同時に来た採用・保存とは順番に処理される
  - 採用でできた版は、項目の `accepted_version_id` からたどれる。版履歴には「提案の採用 N 件」と出る。取り消すときは、版履歴から前の版に戻す。監査ログには入れない（本文の保存を入れていないのと同じ）
  - エディタ（Tiptap）は、保存のたびに Markdown を書き出し直す。表は列の幅をそろえ直すので、人がエディタで保存したあとは、表の行への提案が古くなりやすい
- **レビュー画面**（`/w/{key}/pages/{id}/requests`）：最新の版の本文を、編集画面と同じ見た目の読み取り専用で出し、項目を、指している箇所のすぐ下に並べる。行の範囲から画面のブロックへの対応付けは `apps/admin/src/lib/blockLines.ts`（いちばん上の階層のブロックと、リストの項目・表の行まで。コードブロック・引用・トグルの中の行は、ブロック全体）。差分は Markdown の行の - / + で、変わった語には背景色に加えて打消し線・下線を付ける。指摘は、差分の代わりに本文を出し、「解決済みにする」で片付ける。提案と指摘は、種類の印（アイコンと文字）・中身の形・左の線（実線／点線）で見分ける。項目の下に、返信の一覧と入力欄を出す（`apps/admin/src/components/EditRequestReplies.tsx`）。片付いた項目（採用・却下・解決済み・取り下げ）は、いちばん下に1件ずつ畳んで並べ、開くと中身と返信が読める（返信もできる）。入口は、編集画面のヘッダー（未対応があるあいだ、件数つき）と「…」メニュー
- **気づき方**（個人あての通知は無い）
  - サイドバーの「編集リクエスト」に、**未対応のリクエストがあるページの数**を出す（項目の数でも、リクエストの数でもない。0 のあいだは出さない。ゴミ箱のページは数えない）。数は、自分が採用・却下・解決済み・取り下げ・返信・送信をしたあと（`apps/admin/src/lib/editRequests.ts` の `invalidateEditRequests`）と、60 秒ごとに取り直す（タブが裏にあるあいだは止まり、表に戻ったときに取り直す）。ほかの人や外部のアプリ（MCP）の操作は、この間隔で追いつく
  - wiki ごとの一覧（`/w/{key}/requests`、`apps/admin/src/routes/EditRequestListPage.tsx`）。ページ・出した人（外部のアプリからは「アプリ名・許可した人」）・未対応の項目の数・出した日時・最後の動きを出し、行を押すと、そのページのレビュー画面へ移る。初めは「未対応」（未対応の項目が残っているもの）で絞ってあり、「完了」（未対応の項目が0件。取り下げだけで0件になったものも入る）に切り替えられる（`?status=done`）
  - 一覧の並びは、**出した日時の新しい順**（`edit_requests_wiki_idx`）。「最後の動き」（出した日時、採否を決めた日時、返信の日時のうち、いちばん新しいもの）は表示だけで、並びには使わない。続きを読み込むあいだに採否や返信があっても、行の順番が動かないようにするため。未対応に戻した項目は、決めた日時が消えるので、戻したこと自体は動きに数えない
- **画面から出す**（レビュー画面の「編集リクエストを出す」。`apps/admin/src/components/compose/`）
  - 出すモードに入ると、本文のブロックを選べる。選ぶと、すぐ下に入力欄が開き、「置き換えを提案する」か「指摘だけ書く」を選ぶ。提案は、その範囲が入った小さなエディタ（編集画面と同じ拡張。画像の貼り付けと「@」のページへのリンクも使える）と、理由の入力欄。指摘は、本文（必須）だけで、選んだ範囲をそのまま指す。「提案に追加する」「指摘を追加する」で送信前の項目になり、「送信する」で、全体へのひとことを添えてまとめて送る。送るまで、サーバーには何も残らない（画面を離れると消えるので、離れる前に確かめる）
  - 選べる単位（`apps/admin/src/lib/blockLines.ts` の `selectableUnits`）：段落・見出し・コードブロック・引用・コールアウト・トグル・区切り線・画像はブロックまるごと、リストは項目ごと（入れ子の項目も）、表は行ごと。同じ階層で続いたブロックは、まとめて選べる（項目・行をすべて選ぶと、リスト全体・表全体）
  - 小さなエディタが書き出した Markdown を、選んだ行の範囲に入れられる形に戻す（`apps/admin/src/lib/blockEdit.ts`）。リストの項目は字下げを外して入れ、書き出したものに字下げと元の項目の印（`*` や `1)`）を戻す。表の行は、見出しの行と区切りの行を付けて入れ、書き出したものから選んだ行だけを取り出す（選んでいない見出しの行と、列の数は変えられない）。コードブロック・引用・コールアウト・トグルは、ブロックまるごとを入れる
  - 送る提案は、**変わった行だけ**に絞る（コードブロックの1行だけを直せば、その行だけの提案になる）。置き換えたあとに前後のブロックとつながってしまう書き換え（リストに挟まれた段落を消す、など）は、空行を足して離すか、離せなければ断る
  - 送信が 409（`version_conflict`）で止まったら、書いた提案は残したまま、「最新の版に合わせる」を促す。押すと、新しい本文を読み込み、選んだ範囲の元の文面で場所を探し直す。見つからない・複数ある提案は、理由と書いた内容を出し、取り除くまで送信できない
  - 自分が出したリクエストには、「取り下げる」が出る
- **編集画面を開いたままのとき**：ほかの人の採用で版が進むと、次の自動保存が 409 になる。その版が採用でできたものなら、「採用された変更を取り込む」で、同じ置き換えを手元の内容にかけて続けられる（`GET .../edit-requests/applied?since=`）。採用された箇所を手元でも書き換えていたら取り込めず、手元を捨てて読み直すかを選ぶ。だれかがふつうに保存した版が挟まっていたら、今までどおり
- **MCP**：出す・読む・返信する・取り下げるのは `wiki.suggest`、採用・却下は本文が変わるので `wiki.write`（指摘を解決済みにするのも `wiki.write`）。`wiki.private` の無いアプリは、未公開の編集があるページには出せず（`update_page` と同じ 409 `hidden_edits`）、読める・返信できる・解決済みにできるのは、読めるページの、その許可で出したリクエストだけ。管理画面には、項目も返信も「アプリ名・許可した人」で出る
  - `wiki.suggest` は、足す前に許可したアプリには付いていない。使うには、アプリの側からつなぎ直して、同意し直す
- **API**（`/admin/w/{key}/pages/:id/...`。wiki のメンバーならだれでも）：`POST edit-requests`（出す。入力と検査は MCP の `create_edit_request` と同じで、基準の版が最新でなければ 409 `version_conflict`）、`GET edit-requests`（一覧と、最新の版の本文）、`GET edit-requests/count`、`GET edit-requests/applied?since=`、`POST edit-request-items/:itemId/accept` `reject` `resolve`（指摘を解決済みにする） `reopen`（却下・解決済みを未対応に戻す） `comments`（返信する。`{ body }`）、`POST edit-requests/:requestId/accept-all` `withdraw`。ゴミ箱のページ・アーカイブ中の wiki・別の wiki のページは 404
- **API**（`/admin/w/{key}/edit-requests`。wiki ごと）：`GET edit-requests?status=open|done&limit=&cursor=`（その wiki のリクエスト。出した日時の新しい順で、`nextCursor` を次の `cursor` に渡すと続きが取れる。`GET /pages` と同じ形）、`GET edit-requests/count`（未対応のリクエストがあるページの数 `{ pages }`）。どちらも、ゴミ箱のページのものは入らない。アーカイブ中の wiki は 404
- 項目が基準にしている版は、自動の間引きで消さない。項目の文面（元の文面と置き換え案）にある画像は、画像の掃除で消さない。提案の理由・指摘の本文・返信・ひとことはプレーンテキストなので、画像のパスが書かれていても、使っていることにはしない。ページを完全に削除すると、そのリクエストも、項目・返信ごと消える

## テンプレート

議事録のように同じ形のページを繰り返し作るときの、ひな形。人がページを作るときに選ぶ。

- テンプレートは `page_templates` にページとは別に持つ（wiki ごと）。ツリーにも、公開サイトの書き出し（`/export/public`）にも入らない
- 作り方：管理画面の「テンプレート」（`/w/{key}/templates`）で新しく作るか、エディタの「…」メニューの「テンプレートとして保存」で、いま画面にある内容から作る
- 使い方
  - 本文が空のページ（サイドバーの「＋」やコマンドメニューで作ったばかりのページ）では、本文の上に「テンプレートから始める」が出る。選ぶと変数を置き換えた内容がエディタに入る（ほかの編集と同じく下書きとして自動保存され、一段落すると版になる）。タイトルが「無題」のままなら、テンプレートのタイトルにする
  - コマンドメニュー（⌘K）の「テンプレート「…」で新しいページを作る」、「テンプレート」画面の「このテンプレートでページを作る」
  - 本文の「@」「[[」の「「…」をテンプレート「…」で作ってリンクする」（タイトルは打った名前）
- 変数：ページを作るとき（API の `POST /pages` に `templateId` を渡したとき）に、タイトルと本文の `{date}`（今日の日付、JST）`{datetime}`（今の日時、JST）`{author}`（作った人のメールアドレス）を置き換える（`packages/shared/src/template.ts`）

## ページのアイコン（絵文字）

ページに絵文字を1つ、アイコンとして付けられる。

- 付ける場所：編集画面の、タイトルの左のボタン（狭い画面ではタイトルの上。付いていないときは「…」メニューの「アイコンを付ける…」）。一覧から選ぶか、入力欄に絵文字を1つ入れる（一覧に無い絵文字は、OS の絵文字パネルなどから）。選ぶとすぐに保存され、版は作らない
- 出る場所：管理画面の「すべてのページ」、公開サイトのツリーのナビと記事のタイトル。管理画面のサイドバーと検索結果、公開サイトの `<title>`・ブラウザのタブのアイコン・RSS には出さない
- 公開中のページのアイコンを変えると、公開し直さなくても、次のビルドで公開サイトに出る（アイコンは `pages.icon` にあり、版には入らない）
- 受け付けるのは絵文字1つだけ（`packages/shared/src/emoji.ts`。Unicode の RGI_Emoji。肌の色・つないだ絵文字・旗も1つと数える）。公開サイトの HTML に出るので、API で検査する
- 本文で「:」に続けて名前を打つ（`:memo`、`:メモ`）と、絵文字の候補が出る。候補は、アイコンの一覧と同じもの（`apps/admin/src/lib/emoji.ts`。絵文字のライブラリは入れていない）
- 外のアプリ（MCP）は、`create_page` でアイコンを付けられ、`get_page` で読める。あとから変える道具は無い（公開中のページでは、公開の許可が無くても公開サイトが変わってしまうため）

## ページのカバー画像

ページのタイトルの上に、横長のカバー画像を付けられる（`pages.cover`。版には入らず、選ぶとすぐに保存される）。

- 付ける場所：編集画面のタイトルの上の「カバーを追加」（付いていれば、画像と「カバーを変更」「カバーを削除」）。選ぶ画面は「ギャラリー」（用意した画像）と「アップロード」（自分の画像。`ImageUploader` を使い回す）の2つ（`apps/admin/src/components/PageCover.tsx`）。API は `PUT /pages/{id}/cover`（`{ "cover": "…" | null }`）。ページを作るとき（`POST /pages`）にも `cover` を渡せる
- 値は画像のパス（`packages/shared/src/cover.ts`）：アップロードした PNG・JPEG・WebP（`/images/{24文字}.(png|jpg|webp)`。GIF は動くので使えない。大きさの上限は本文の画像と同じ 5MB）か、用意した画像（`/covers/{key}.svg`）
- 用意した画像は、自作の SVG 8枚（`apps/admin/public/covers/` と `apps/site/public/covers/` に同じものを置く。どちらのオリジンでも同じパスで見える。`packages/shared/src/cover.test.ts` が、2つの中身が同じで `COVER_PRESETS` と合っていることを確かめる）。増やすときは、`COVER_PRESETS` と両方のディレクトリに足す。出典とライセンスは `NOTICE`
- 高さは固定（管理画面は 120px〜200px、公開サイトは 200px〜240px）で、画像は中央を `object-fit: cover` で切り抜く。切り抜きや位置の調整は無い
- 公開サイト：`ManifestPage.cover` / `ManifestUnlistedPage.cover` に入る（公開・限定公開のページだけ。非公開のページのカバーは出ない）。`Article.astro` が `<h1>` の上に `loading="eager"`・幅と高さつき・alt 空で出し、拡大の対象にはしない。公開中のページのカバーを変えると、公開し直さなくても次のビルドで反映される（`publish_events.kind` は `cover`）。OGP の画像に使うときは、`ManifestPage.cover` を絶対 URL にして使う
- アップロードしたカバーは、画像の掃除（週1回）で「参照されている」ものとして残す（`pages.cover`、ゴミ箱のページも含む）
- 管理画面の一覧・リンクのプレビューには、カバーは出さない

## プレゼンモード（編集画面）

編集画面で開いているページを、そのままスライドとして発表できる。エディタの「…」メニューの「プレゼンモードで表示」か、コマンドメニュー（⌘K）の「このページをプレゼンモードで表示」で始める（`apps/admin/src/components/Presentation.tsx`）。公開サイトの記事にも同じものがある（`apps/site/README.md` の「プレゼンモード」）。

- スライドにするのは、始めたときに画面にあった内容（まだ版になっていない変更も含む）。公開・非公開は問わない。プレゼン中は編集できず、エディタの内容とスクロール位置は変わらない。下書きの自動保存は、裏でそのまま続く
- 画面全体を覆って出す。URL は変わらない
- スライドの分け方（`apps/admin/src/lib/slides.ts`。公開サイトと同じ分け方にするが、コードは共有しない）
  - 1枚目はページのタイトルだけ（タイトルが空なら作らない）
  - 本文は、いちばん上の階層にある見出し（深さは問わない）ごとに新しいスライドにする。区切り線（`---`）でも区切り、区切り線そのものは出さない
  - 引用・コールアウト・トグル・リスト・表の中の見出しや区切り線では区切らない。最初の見出しより前の本文は、タイトルの次のスライドになる。中身の無いスライドは作らない（何も書いていない行は数えない）
- スライドの中身は、エディタと同じ拡張の読み取り専用の Tiptap で出す。見た目はエディタと同じもの（`MarkdownEditor.tsx` の `editorContentSx`）を、画面の幅に合わせて 1.15〜2 倍にする。トグルは閉じた状態から始まり、押すと開く。チェックリストは押しても変わらない。リンクは新しいタブで開く
- 1枚に収まらないスライドは、収まるまで全体を縮める（0.5 倍まで）。それでも収まらなければ、そのスライドの中で縦にスクロールする
- 操作部品はいつも出ている：右上に「全画面表示」（Fullscreen API が使えない環境では出ない）と「プレゼンモードを終了」、下に「前のスライド」「次のスライド」と、いま何枚目か

| キー | 動き |
|---|---|
| Space / → / PageDown | 次のスライド |
| ← / PageUp | 前のスライド |
| Home / End | 最初 / 最後のスライド |
| F | 全画面表示にする／やめる |
| Esc | 全画面ならやめる。全画面でなければプレゼンモードを終了 |

ボタンやリンクにキーボードでフォーカスを置いているときの Space は、その部品を押す。プレゼン中は、管理画面のほかのショートカット（「?」のガイド、⌘K、⌘S、⌘.）は動かない。

## アクセス解析

Google Analytics（GA4）とサーチコンソールにつないだ wiki の数字を、Google の画面を開かなくても、管理画面の「アクセス解析」（`/w/{key}/analytics`）でつかめるようにする。細かい分析は、画面のリンクから Google の画面で行う。記事ごとの閲覧数も、ここ（「よく読まれた記事」）と Google の画面で見る（公開サイトで閲覧を数える仕組みは、Workers の無料プランの呼び出し回数に収めるため外した）。

- **出すもの**（その wiki を開ける人ならだれでも見られる）
  - 連携の状態：GA・サーチコンソールそれぞれの「接続済み」「未設定」「エラー」と、取得した日時、失敗の理由と直し方、サーチコンソールに送ったサイトマップの状態
  - GA の概要：利用者数・表示回数（前の同じ長さの期間との増減つき）と、日ごとの推移
  - よく読まれた記事：表示回数の上位20件。`/p/{id}` と、廃止したツリー経由の `/t/{treeKey}/{id}`（過去の数字に残る）は同じ記事として合わせ、題名から管理画面の記事へ移れる。その wiki の記事に結びつかないパス（トップ・検索・削除済みの記事など）は、パスのまま出す
  - 流入元：チャネルごとのセッション数
  - 検索（サーチコンソール）：クリック数・表示回数・CTR・平均掲載順位の合計と日ごとの推移、検索キーワードとページの上位20件
- **期間**は、昨日までの 7日・28日・90日（既定は28日）。日付の区切りは Google の側に従う（GA はプロパティのタイムゾーン、サーチコンソールは太平洋時間）。サーチコンソールの数字は2〜3日遅れて出る
- **Google へは、サービスアカウントで読みにいく**（人のログインとは切り離す。だれが開いても同じ数字が出る）。スコープは読み取りだけ（`analytics.readonly`、`webmasters.readonly`）。鍵で署名した JWT をアクセストークンに換える（`apps/api/src/analytics/google.ts`。Workers で動くよう、署名は Web Crypto）
  - 鍵は Worker のシークレット `GOOGLE_SERVICE_ACCOUNT_JSON`（Google Cloud でダウンロードした JSON そのまま）。**未設定なら、この機能だけが無効**で、画面には「まだつないでいません」と手順を出す。ほかの画面は今までどおり動く。JSON として読めない値が入っていても、ほかの画面は止めず、画面にそう出す
  - 鍵とアクセストークンは、管理画面へ返さず、ログにも出さない。返すのはサービスアカウントのメールアドレスだけ。Google の応答の本文（エラーの文）も返さず、失敗の種類だけを返す
  - Google へ送る問い合わせは、その wiki のプロパティ ID と公開サイトの URL（`{origin}/`。サーチコンソールは「URL プレフィックス」のプロパティ）だけを使う
- **取った数字は DB に控える**（`analytics_snapshots`：`wiki_id` / 種類 / 期間 / 問い合わせ先 / 中身の JSON / 取得日時 / 最後に問い合わせた日時 / 失敗の理由）。前もっては取らず、画面を開いたときに取る
  - 同じ wiki・同じ期間は、1時間のあいだ Google へ問い合わせない。「数字を取り直す」で取り直せるが、1分おきまで
  - GA とサーチコンソールは別々に取り、片方が失敗しても、もう片方は出す。Google 側の失敗（権限なし・プロパティが無い・上限・時間切れ）は 500 にせず、連携の状態として出す。前に取れたぶんがあれば、「◯時点の数字」として出し続ける。失敗したあとは、5分のあいだ開き直しても問い合わせない
  - プロパティ ID を変えたら、前のプロパティの控えは出さない。記事の題名は控えず、出すときにその wiki の記事と結びつける
- API：`GET /admin/w/{key}/analytics?days=28`、`POST …/analytics/refresh`（取り直す）、`GET …/analytics/connection`（サービスアカウントのメールアドレス）、`POST …/analytics/check`（「接続を確かめる」）

### 使えるようにする

**1回だけ行うこと**（管理画面を運用する人）

1. [Google Cloud](https://console.cloud.google.com/) のプロジェクト（ログイン用の OAuth クライアントと同じものでよい）の「API とサービス → ライブラリ」で、**Google Analytics Data API** と **Google Search Console API** を有効にする
2. 「IAM と管理 → サービスアカウント」でサービスアカウントを作る（名前は自由。ロールは付けなくてよい）。作ったサービスアカウントの「鍵」で、JSON の鍵を作ってダウンロードする
3. GitHub の Settings → Secrets and variables → Actions に、シークレット `GOOGLE_SERVICE_ACCOUNT_JSON` として、ダウンロードした JSON の中身をそのまま登録する
4. Actions の「Deploy」を手動実行する（シークレットは、デプロイのときに Worker へ入る）。管理画面の「設定」に、サービスアカウントのメールアドレス（`…@….iam.gserviceaccount.com`）が出れば、鍵は読めている

**wiki ごとに行うこと**（その wiki のオーナー。画面の「設定」に同じ手順が出る）

1. GA の「管理 → プロパティの詳細」の右上に出ている**プロパティ ID**（数字だけ）を、「設定」の「プロパティ ID」に入れて保存する
2. GA の「管理 → プロパティのアクセス管理」で、サービスアカウントのメールアドレスを「閲覧者」として足す
3. サーチコンソールの「設定 → ユーザーと権限」で、同じメールアドレスをユーザーとして足す（権限は「制限付き」で足りる）。プロパティは、公開サイトの URL を「URL プレフィックス」で登録したもの（「設定」の手順で作るもの）が要る。ドメイン プロパティ（`sc-domain:`）だけでは読めない
4. 「設定」の「接続を確かめる」を押す。だめなときは、理由と直し方が出る

手元で試すときは、`apps/api/.env` の `GOOGLE_SERVICE_ACCOUNT_JSON` に、JSON を1行にして入れる。

## SNS 連携

wiki ごとに、その wiki の SNS アカウントをつなぐ。いまつなげるのは **X** だけ。管理画面の「設定」の「SNS」タブ（`/w/{key}/settings/sns`）で、wiki の管理者（とオーナー）が行う。

- **できること**：X のアカウントをつなぐ・外す、つないだアカウントの名前（`@...`）とつないだ人・日時を見る、**テスト投稿**（文面を入れて、実際に1件ポストし、連携が働いているかを確かめる）。記事を公開したときのお知らせのポストは、まだ無い（これから足す。ポストは `apps/api/src/sns/service.ts` の `postAsWiki` を通す）
- **つなぎ方**：「X と連携する」を押すと X の認可の画面に移り、許可すると「SNS」タブに戻る（OAuth 2.0 の認可コード + PKCE）。X のパスワードは、この管理画面には渡らない。もらう権限は `tweet.read` `tweet.write` `users.read` `offline.access`（ポストと、アカウント名の確認、許可を持ち続けるための更新）
  - つなぐのは、**X の画面でログインしているアカウント**。別のアカウントにしたいときは、先に X の側でアカウントを切り替える
  - wiki と X のアカウントは1対1（1つの wiki に1つ）。同じアカウントを、複数の wiki につないでもよい。つなぎ直すと、新しいアカウントで置き換わる
  - 認可を始めてから戻るまでは10分。戻ってきたときに、始めた人がいまもログインしていて、その wiki の管理者であることを確かめ直す
- **トークン**（アクセストークンと、更新用のトークン）は、`SNS_TOKEN_KEY` を鍵に暗号化して DB に持つ（AES-256-GCM。`apps/api/src/crypto/token.ts`）。管理画面にも、監査ログにも、ログにも出さない
  - アクセストークンの期限（2時間）が近ければ、ポストの前に更新する。X の更新用のトークンは1回きりで、使うたびに新しいものに置き換わるので、行をロックして更新し、同じトランザクションで保存する
  - **`SNS_TOKEN_KEY` を変えると、つないであるアカウントは使えなくなる**（復号できない）。変えたら、wiki ごとに連携し直す
- **連携が切れたとき**（X の側で連携を外した・長く使わず許可の期限が切れた）は、テスト投稿の結果にそう出るので、「X と連携し直す」から許可し直す
- **解除**すると、行を消し、X の側のトークンも無効にする（X に届かなくても、解除は済ませる）。これまでのポストは消えない
- **1ポストの長さ**は X の数え方（半角は1、全角は2、URL は長さにかかわらず23。上限280）で確かめる。日本語だけなら140文字まで。絵文字の合成までは追わないので、合成した絵文字は X より多めに数える
- 監査ログに、連携・解除・テスト投稿を残す（「監査ログ」）
- API：`GET /admin/w/{key}/sns`（状態）、`POST .../sns/x/connect`（認可を始める。X の画面の URL を返す）、`GET /auth/x/callback`（X から戻る所）、`POST .../sns/x/disconnect`、`POST .../sns/x/test-post`
- データ：`wiki_sns_accounts`（`id` / `wiki_id` / `provider`（`x`）/ `external_id`（X のアカウント ID）/ `username` / `display_name` / `access_token_enc` / `refresh_token_enc` / `expires_at` / `scopes` / `connected_by` / `connected_by_label` / `connected_at` / `updated_at`）。`wiki_id` と `provider` の組で1行

### 使えるようにする

X の開発者アプリ（OAuth 2.0 のクライアント）を、この管理画面の全体で1つ用意する。**未設定なら、この機能だけが無効**で、「SNS」タブに「設定がまだ登録されていない」と出す。ほかの画面は今までどおり動く。

1. [X の開発者ポータル](https://developer.x.com/)で、プロジェクトとアプリを作る。ポストを作れるプランであること（料金と上限は、X の側で確かめる）
2. アプリの「User authentication settings」を設定する
   - App permissions：**Read and write**
   - Type of App：**Web App, Automated App or Bot**（Confidential client）
   - Callback URI / Redirect URL：`https://wiki-admin.hatchery-works.com/api/auth/x/callback`（手元で試すなら `http://localhost:5173/api/auth/x/callback` も足す）
   - Website URL：管理画面か公開サイトの URL
3. 「Keys and tokens」の **OAuth 2.0 Client ID and Client Secret** を控える（API Key / API Key Secret や Bearer Token ではない）
4. GitHub の Settings → Secrets and variables → Actions に、`X_CLIENT_ID`・`X_CLIENT_SECRET`・`SNS_TOKEN_KEY`（`openssl rand -base64 48`。32文字以上）を登録し、Actions の「Deploy」を実行する
5. 管理画面の「設定」の「SNS」タブで「X と連携する」を押し、つないだあと「テスト投稿する」で確かめる

3つのうち1つでも無い（または `SNS_TOKEN_KEY` が32文字より短い）と、未設定として扱う。手元で試すときは、`apps/api/.env` に同じ3つを入れる。

## 運用コスト

サービスの使い方（使用量）を、管理画面の「全体の管理」の「コスト」タブ（`/costs`。オーナーだけ）で見る。いまは **DB（Neon）だけ**を取る。

- **使用量だけを出し、金額は出さない**。Neon の消費量 API は使用量（コンピュート・ストレージ・転送）を返し、請求額は返さない（確かめたのは公式の API リファレンスだけで、実際の API は叩いていない）。使用量から料金は計算しない
- **取り方**：1日1回（`wiki-worker` の `0 18 * * *`。JST の午前3時。間引きと同じ cron）に、ワーカーが API の `POST /internal/costs/collect`（`CRON_TOKEN`）を呼ぶ。API が Neon の `GET /consumption_history/v2/projects`（月ごと・組織のすべてのプロジェクトの合計）を読み、今月と前月（UTC の月）を `cost_snapshots` に控える。5分おきの cron では動かさない
- **失敗**：サービスごとに独立していて、1つが失敗しても、ほかは控える。失敗した理由（種類だけ。鍵と応答の本文は残さない）を今月の行に書き、前に取れた数字はそのまま残して、画面は「◯時点の数字」として出す
- **残す期間**：サービスと月ごとに1行で、消さない（1年で12行ほど）。画面に出すのは今月と前月だけ
- **見られる人**：オーナーだけ。`GET /admin/costs` は、ほかのロールに 403。鍵は返さず、設定されているかどうかだけを返す
- データ：`cost_snapshots`（`service` / `period`（`YYYY-MM`）/ `usage`（項目名 → 値の JSON）/ `fetched_at` / `attempted_at` / `error`）。`service` と `period` の組で1行
- **サービスを足すとき**：`packages/shared/src/costs.ts` の `COST_SERVICES` と `COST_USAGE_METRICS` に足し、`apps/api/src/costs/` に `CostSource`（`neon.ts` と同じ形）を作って、`costSourcesFromConfig` に足す

### 使えるようにする

**未設定なら、この機能だけが無効**で、「コスト」タブに「まだつないでいません」と出す。ほかの画面は今までどおり動く。

1. 使っている Neon のプランが、消費量の API を使えるものか確かめる（公式のドキュメントでは Launch・Scale・Agent・Business・Enterprise。Free は 403 になり、画面に理由が出る。使えるようになったあとの数字だけが取れる）
2. Neon のコンソールで、組織の API キーを作る（組織を読める権限のもの）。組織 ID は、組織の設定に出ている
3. GitHub の Settings → Secrets and variables → Actions に、`NEON_API_KEY` と `NEON_ORG_ID` を登録し、Actions の「Deploy」を実行する
4. 次の取得（JST の午前3時）のあとで、「コスト」タブに出る。すぐ見たいときは、`wiki-admin` の Cron ワーカーのログで確かめるか、`POST /internal/costs/collect` を `CRON_TOKEN` で呼ぶ

2つのうち1つでも無いと、未設定として扱う。手元で試すときは、`apps/api/.env` に同じ2つを入れる。

## Routine（ワークフローが呼ぶ Claude Routine）

「全体の管理」の「Routine」タブ（`/routines`。オーナーだけ）に、ワークフローが呼ぶ **Claude Routine**（Claude Code の routine の API トリガー）を、名前・URL・トークンで登録する。各 wiki のワークフローは名前で選ぶだけにして、wiki ごとにトークンを入れる手間を無くす。「テスト実行」で、登録したものが呼べるか確かめる（Routine の回数を1回使う）。

- **呼び方**（公式ドキュメント <https://platform.claude.com/docs/en/api/claude-code/routines-fire> で確かめたもの）：`POST https://api.anthropic.com/v1/claude_code/routines/{routine_id}/fire`、`Authorization: Bearer {Routine ごとのトークン}`、`anthropic-version: 2023-06-01`、本文 `{ "text": "…" }`。成功は 200 で、セッションの ID と URL が返る。実験的な API で、形が変わりうる。実装は `apps/api/src/workflows/routine.ts` の `fireRoutine`
- **URL**：`https://api.anthropic.com/v1/claude_code/routines/…/fire` の形だけ受け付ける（ほかのホストへ叩かせない）
- **トークン**：`ROUTINE_TOKEN_KEY` を鍵に暗号化して DB に持つ（`apps/api/src/crypto/token.ts`。SNS と同じ仕組みで、鍵は別）。画面・API の応答・監査ログ・ログに出さず、登録済みかどうかだけを返す。**`ROUTINE_TOKEN_KEY` を変えると、登録済みのトークンは使えなくなる**（Routine ごとに入れ直す）
- **見られる人**：オーナーだけ（`/admin/routines`）。ほかのロールは 403
- **未設定なら**、一覧は読めるが、登録・変更・削除・テスト実行は 503 `routine_not_configured`。ほかの画面は今までどおり動く
- **失敗の分け方**：`fireRoutine` は、再試行できる失敗（ネットワーク・タイムアウト・上限 429・相手の不調 5xx）と、できない失敗（トークン違い・権限なし・URL 違い・受け付けられない・応答が読めない）を型で分けて返す。呼び出しに冪等キーは無く、タイムアウトのあとでも相手でセッションが始まっていることがある
- データ：`workflow_routines`（`id` / `name`（一意）/ `url` / `token_enc` / `created_at` / `created_by`）
- **消せない Routine**：どこかのワークフローのブロックのアクションが使っている Routine は、削除が 409 `routine_in_use`（`details` に、使っている wiki ごとのブロックの数）。先に、各 wiki のブロックから外す

### 使えるようにする

1. GitHub の Settings → Secrets and variables → Actions に、`ROUTINE_TOKEN_KEY`（`openssl rand -base64 48`。32文字以上。`SNS_TOKEN_KEY` とは別の値）を登録し、Actions の「Deploy」を実行する。手元で試すときは、`apps/api/.env` に入れる
2. Claude Code（claude.ai/code/routines）で Routine を作り、API のトリガーを足して、URL とトークン（作ったときに一度だけ表示される）を控える
3. 「全体の管理」の「Routine」タブから登録する

## ワークフロー（wiki ごとに名前つきで複数）＞ブロック

サイドバーの「ワークフロー」（`/w/{key}/workflows`。管理者だけ。設定のタブだった頃の `/settings/workflows` も、ここへ移す）は、この wiki のワークフローの一覧（`components/DataList.tsx`。行を押すと詳細へ移る）。用途ごと（例：校正、公開前チェック）に名前を付けて、**1つの wiki に20個まで**（名前は50文字まで、同じ wiki の中で重ならない）作れる。1つのワークフローを開くと（`/w/{key}/workflows/{workflowId}`。タブの題は「{名前} - ワークフロー」）、そのワークフローの「ブロック」と「実行の履歴」が出る。名前の変更と削除もここ（削除すると、ブロックと実行の履歴もいっしょに消える。確認つき）。

1つのブロックは「1つのトリガー ＋ 上から順に行うアクションの並び（1〜10件）」で、ブロック同士は独立している（順番は無く、作った順に出す。同じ内容が重なってもよい）。実行の取りこぼしを Cron が拾う仕組みは、下の「Cron」の節の `cron:workflow`：`pending` と、`running` のまま10分たった実行を1回に20件まで続きから動かし、3回で失敗を確定して監査ログ `workflow_run_fail` と通知を出す。タグが付いたときは、wiki の中のどのワークフローのブロックでも、トリガーが合えば実行を積む（実行はブロック単位。実行の記録に `workflow_id` を入れて、履歴をワークフローごとに分ける）。

- 種類：トリガーは「タグが付いたとき」、アクションは「Routine を呼ぶ」「タグを外す」。型は `packages/shared/src/workflow.ts` の判別付きユニオン（`type` で見分ける）。種類を足すときは、そこと、API の `apps/api/src/workflows/blocks.ts` の種類ごとの表（`TRIGGER_COLUMNS` `ACTION_COLUMNS`。足し忘れると型エラー）、実行側の表に足す
- API（`/admin/w/{key}/workflow`。読むのはメンバーなら誰でも、作る・変える・消すのは管理者だけ。別の wiki のワークフローは 404）：
  - `GET /`（一覧。ブロックの数つき）・`POST /`（`{ name }`。名前の重なりは 409 `workflow_name_taken`、21個目は 409 `workflow_limit`）・`GET /{workflowId}`・`PATCH /{workflowId}`（名前の変更）・`DELETE /{workflowId}`（ブロックと実行の履歴もいっしょに消える）
  - ブロックはワークフローの下：`GET /{workflowId}/blocks`・`POST /{workflowId}/blocks`・`PUT /{workflowId}/blocks/{id}`（アクションの並びごと置き換える）・`DELETE /{workflowId}/blocks/{id}`。別の wiki のタグ・登録されていない Routine は 400
  - `GET /{workflowId}/runs`（実行の履歴。管理者だけ。`status` `limit` `cursor`）
  - `GET /admin/w/{key}/routines`（ブロックで選ぶための Routine の ID と名前だけ。管理者だけ）
- 監査ログ：ワークフローの作成 `workflow_create`・名前の変更 `workflow_rename`・削除 `workflow_delete`（いっしょに消えたブロックと履歴の数つき）。ブロックは `workflow_block_create` / `_update` / `_delete`
- タグを消すと、そのタグがトリガーのブロックは消え、「タグを外す」で指しているアクションは取り除かれ、アクションが無くなったブロックも消える（監査ログに残る）。ワークフロー自体は、ブロックが0件になっても残る
- データ：`workflows`（`wiki_id` / `name`（wiki の中で一意）/ `created_at` / `created_by`）、`workflow_blocks`（`workflow_id`（ワークフローを消すと消える）/ `wiki_id` / `trigger_type` / `trigger_tag_id`）、`workflow_actions`（`block_id`（ブロックを消すと消える）/ `position` / `type` / `routine_id` / `tag_id`。`type` ごとに必要な列を check で縛る）、`workflow_runs`（`workflow_id`（ワークフローを消すと、履歴も消える）。`block_id` は、ブロックだけ消えたときは null になって履歴は残る）
- 移行（`0043_workflows`）：すでにブロックか実行の履歴がある wiki ごとに「ワークフロー」という名前のワークフローを1つ作り、既存のブロックと履歴をそこへ入れてから、`workflow_id` を `NOT NULL` にした。どちらも無い wiki には作らない
- 履歴の保持期間（終わって90日）と、日次の掃除（`cleanup.ts`）は、ワークフローが増えても変わらない

## スマホから使う（PWA）

管理画面はホーム画面に置ける（Web App Manifest と Service Worker。`apps/admin/vite.config.ts` の `vite-plugin-pwa`）。置いたものから開くと、ブラウザの枠なしで出る。

- Service Worker が覚えるのは、ビルドした画面のファイル（JS・HTML・アイコン）だけ。API の応答（`/api/*`）とアップロードした画像（`/images/*`）は覚えない。オフラインでは画面の枠までは出るが、内容の読み込みと編集はできない
- `/api/*` `/export/*` `/internal/*` `/images/*` `/health` への画面遷移には、Service Worker が手を出さない（Google ログインのリダイレクトがここを通る）。`apps/api/wrangler.toml` の `run_worker_first` に経路を足したら、`vite.config.ts` の `navigateFallbackDenylist` にも足す
- 新しい版をデプロイしても、開いている画面は勝手に切り替わらない。「新しい版があります」と出し、「更新する」を押したときに読み込み直す（`apps/admin/src/components/UpdatePrompt.tsx`）。新しい版が出ていないかは、画面を開いたとき、裏から戻ったとき、開いたままなら1時間ごとに確かめる。「あとで」を選んだときは、管理画面をすべて閉じて開き直すと新しい版になる
- 管理画面の JS は、ライブラリ（`react` `mui` `editor`。`vite.config.ts` の `manualChunks`）と、重い画面ごと（`apps/admin/src/router.tsx` の `lazyScreen`）のファイルに分けてある。エディタ（TipTap・ProseMirror）は、エディタを使う画面を開くときに読む。どの画面にも出る部品（サイドバー・コマンドメニューなど）から `src/editor` や画面のファイルを import すると、エディタが最初に読む JS に戻り、ビルドが止まる（`vite.config.ts` の `wiki:first-load`）
- 分けたファイルも Service Worker が全部覚えるので、新しい版をデプロイして古いファイルがサーバーから消えても、開いている画面は覚えているファイルで動く。Service Worker がまだ効いていない画面（初めて開いた画面など）や、ほかのタブで「更新する」を押したあとの古いタブでは、画面のファイルが取れないことがある。そのときは、その場に「この画面を読み込めませんでした」と「画面を読み込み直す」を出す（`apps/admin/src/routes/lazyScreen.tsx`）
- Service Worker は `pnpm dev` では動かない。手元で確かめるときは `pnpm --filter @wiki/admin build` のあと `pnpm --filter @wiki/admin preview --port 5173`（API の `ADMIN_ORIGIN` と同じオリジンで開く）
- サイドバーの並び替え（ツリー、スター）は、タッチでは長押ししてからドラッグする（すぐ動かすとスクロールになる）
- サイドバーの行のボタン（「…」「＋」）は、マウスで操作する端末（`(hover: hover) and (pointer: fine)`）ではマウスを乗せたときとキーボードのフォーカスがあるときだけ出す。指で操作する端末では、乗せる操作が無いので、いつも出す
- キーボードだけで使うとき：画面の先頭の「本文へ移る」（スキップリンク。Tab を1回押すと出て、Enter で `main` へ移る）で、サイドバーを飛ばして本文へ着く。サイドバーの「ドキュメント」のツリーは WAI-ARIA の Tree View として動く（`Sidebar.tsx`）
  - Tab で入るのは1行だけ（開いているページの行。無ければ先頭の行。入ったあとは、最後にフォーカスした行）で、もう1回 Tab を押すとツリーを抜ける。行の中のリンクと「たたむ」「…」「＋」は Tab の順に入れない（マウスとタッチの操作は変わらない）
  - ↑↓：前後の行　→：たたんでいれば開く、開いていれば最初の子の行へ　←：開いていればたたむ、たたんでいれば親の行へ　Home / End：先頭 / 末尾の行　Enter：そのページを開く
  - 行の「…」と「＋」は、行にフォーカスがあるときのショートカットで開く。Shift+F10（またはメニューキー）で「…」のメニュー、Shift+Enter でその下に新しいページを作る。メニューを閉じるとフォーカスは行に戻る
  - ページが多く（500 超）行を間引いて描いているときも同じ。画面の外の行へ移るときは、その行まで送ってからフォーカスする。Tab で入る行は、送って見えなくなっても描いたままにする
- アイコンは `apps/admin/public/` の PNG（`favicon.svg` と同じ絵柄。`icon-maskable-512.png` は OS が形を切り抜くので、端まで塗って絵柄を中央に寄せてある）

## 公開サイトの外観（テーマ）

公開サイトの見た目を wiki ごとに変えられる。管理画面の「設定」の「外観」タブ（`/w/{key}/settings/appearance`）で、wiki の管理者（とオーナー）だけが変えられる。選んだテーマは、その wiki の管理画面（`/w/{key}/...`。メニューやダイアログも）の配色にも使う。
  - 色（背景・文字・枠線・リンク・成功・警告・危険・マーカー）をテーマから写す（`apps/admin/src/lib/presetPalette.ts`）。背景画像（方眼・水玉・星）は、画面の後ろに固定で敷く（`apps/admin/src/components/ThemeBackdrop.tsx`。公開サイトと同じ画像）。背景のあるテーマでは、本文側の面を透明にして画像を見せる（カード・サイドバーは不透明のまま）。飾り（フクロウ）と、wiki が自分で入れた背景画像は、本文の読みやすさのため管理画面には出さない。差分・検索の背景は、テーマの色を面の色に薄く混ぜて作り、文字が 4.5:1 以上で読めることを `presetPalette.test.ts` が全テーマで確かめる
  - ライト版・ダーク版の両方を持つテーマは、端末の設定に追従する。片方だけのテーマは、端末の設定に関わらずいつもその版（`<html>` にクラスを付けて切り替える。`apps/admin/src/main.tsx`）
  - 「シンプル」は、これまでの管理画面の配色のまま（手で整えた値）。wiki の外の画面（wiki の一覧・全体の管理）も既定の配色
  - 選んだテーマの key は wiki の一覧（`GET /admin/wikis` の `themePreset`）に入り、wiki ごとに最後に開いたものを localStorage（`wiki.admin.themePresets`）に覚える。開いた瞬間から同じ配色で出し、色が切り替わるのを見せないため
  - コードの色分けの色は CSS 変数 `--hl-*`（`theme.ts` が `:root` に置く）。管理画面の `prefers-color-scheme` を直接見ない

- 変えられるのは次の4つだけ。**色は、用意したテーマから選ぶだけ**（読みやすさが崩れないようにするため。色を1つずつ自由に決める設定、独自の CSS は無い）。フォントは変えられない
  | 項目 | 内容 | 既定 |
  |---|---|---|
  | サイト名 | ヘッダー・`<title>`・RSS・フッターに出る名前（1〜40文字）。wiki の表示名（`wikis.name`）と同じもの | wiki を作ったときの名前 |
  | テーマ | 背景・文字・枠線・リンクなどの色の組み合わせ。ライトの端末で使うものとダークの端末で使うものを1つずつ選ぶ（端末の設定 `prefers-color-scheme` で切り替わる） | シンプルライト / シンプルダーク |
  | ロゴ | ヘッダーのサイト名の位置に、高さ 32px で出す画像。代替テキストはサイト名。無ければサイト名を文字で出す | 無し |
  | ファビコン | ブラウザのタブに出るアイコン | `favicon.svg` |
- **テーマは `packages/shared/src/theme.ts` の `THEME_PRESETS`**（名前・ライトかダークか・`global.css` の色の変数一式）に定義する。テーマを足すときは、この配列に1件足す。管理画面の見本・API の検証・公開サイトの CSS は、これを見て動く。文字とリンクの色が背景に対してコントラスト比 4.5:1 以上（WCAG）であることを、`theme.test.ts` が全テーマで確かめる
  - 保存できるのは、定義にあるテーマの key だけ（ライト用にはライトのテーマ、ダーク用にはダークのテーマ）。公開サイトも、知らない key は既定のテーマに戻して読む
  - 古い形の `theme`（アクセント色 `accentLight` / `accentDark` だけが入っているもの）は、既定のテーマとして読む（アクセント色は引き継がない）
- **テーマに付く背景画像と飾り**：「手書きノート風」（方眼）・「パステル」（水玉）・「宇宙」（星。白・青白・淡い黄色）は背景画像を、「フクロウ」は画面の右下に飾り（フクロウのアイコン）を持つ。画像は、テーマの定義（`background` / `ornament`）の中に、**この wiki のために描いた SVG**として持つ（外部の素材は使っていない。出どころ・ライセンスの確認は要らない）。公開サイトは CSS の変数（`--bg-image` `--ornament-image` ほか）に `data:` の URL で入れ、本文の後ろに固定で敷く（`global.css` の `.theme-backdrop` `.theme-ornament`。`aria-hidden`・`pointer-events: none`、飾りは幅 800px 以下と印刷では出さず、背景画像も印刷では出さない）。「宇宙」はさらに、背景の後ろをロケットが左下から右上へ横切る（テーマの定義の `motion`。公開サイトは `global.css` の `.theme-motion` と `--motion-*` の変数、管理画面は `ThemeBackdrop.tsx` が同じ動きにする。`aria-hidden`・`pointer-events: none`、印刷と `prefers-reduced-motion: reduce` では出さない。別のテーマにロケット以外の動くものを足すときも、`motion` に1件書く）。画像は色の上に薄く重ねるので、定義に「いちばん濃い色（`ink`）と不透明度（`alpha`）」を書き、その重なりでも文字とリンクが 4.5:1 以上になることを `theme.test.ts` が確かめる（SVG の不透明度が `alpha` を超えていないことも確かめる）
- **wiki が自分で入れる背景画像**（ライト用・ダーク用。`wikis.theme` の `backgroundLight` / `backgroundDark`）は、PNG・JPEG・WebP、2MB まで（`POST /admin/w/{key}/appearance/background-images`。置き場所と配り方はロゴと同じ）。入れると、テーマの背景画像の代わりに、そのテーマの背景色を 82% で重ねて（`CUSTOM_BACKGROUND_VEIL`、固定）画面いっぱいに出す。自分で入れた画像は読みやすさを確かめられないので、管理画面の「背景画像」の「i」に、読みにくくなることがあると書いてある。取り消すとテーマの画像（無いテーマは単色）に戻る
- **ロゴとファビコン**は PNG・WebP、1ファイル 512KB まで（SVG は受け付けない）。置き場所は本文の画像と同じ R2 のバケットで、`/images/{name}` で配る
- **保存するまで公開サイトには反映しない**。保存すると `publish_events` に記録し、いつものデバウンスを通して公開サイトをビルドし直す（反映には数分かかる）。公開サイトは、ビルドのときに wiki ごとのテーマの色（CSS の変数一式）・ロゴ・ファビコン・名前を出し分け、表示のたびに設定を取りに行くことはしない
- データ：`wikis.theme`（jsonb：`preset`（テーマの key。ライト版・ダーク版の両方を持つテーマは端末の設定に合わせて切り替わり、片方だけのテーマはいつもその版）/ `logo` / `favicon` / `backgroundLight` / `backgroundDark`）。null や欠けた項目は既定として読む。公開用のデータ（`/export/public`）に、wiki ごとの `theme` として入る
- サイト名を変えたときは、「wiki の管理」から名前を変えたときと同じく監査ログに残す（変更前と変更後の名前）。テーマ（色・ロゴ・ファビコン）の変更は、いまは監査ログに残さない。前の設定に戻す機能（履歴）は無い

## 公開サイトのトップページ

公開サイトのトップ（`/`）は、**自由記述＋新着記事**。自由記述（紹介文など）は wiki ごとに、管理画面の「設定」の「トップページ」タブ（`/w/{key}/settings/home`）で、wiki の管理者（とオーナー）だけが書ける（API は `GET` / `PUT /admin/w/{key}/home`）。

- 自由記述は、ページの本文と同じエディタ（`MarkdownEditor`）で書く。保存するのは Markdown（記事と同じ記法・同じ描き方。本文中の内部リンクの解決も記事と同じ）で、10,000 文字まで。新着記事の上に出す。空（空白だけを含む）なら何も出さず、新着記事だけになる
- **保存するまで公開サイトには反映しない**。値が変わったときだけ `publish_events`（`wiki_home`）に記録して公開サイトをビルドし直し（アーカイブ中の wiki ではしない）、監査ログに残す（中身は残さない）。下書きと公開を分ける仕組みは無い
- トップにツリー（`/t/{key}/`）へのリンクは出さない。ツリーの一覧のページ（`/t/{key}/`）は廃止し、トップへ 301 で移す
- データ：`wikis.home`（jsonb：`introMd`）。null や正しくない値は既定（空）として読む（`packages/shared/src/home.ts` の `resolveHome`）。あとでトップに出す部品の並びや表示の切り替えを足せるよう、文字列ではなくオブジェクトで持つ。公開用のデータ（`/export/public`）に、wiki ごとの `home` として入る

## デプロイ

`main` に入ると GitHub Actions（`.github/workflows/deploy.yml`）が、検査 → マイグレーション → 管理画面+API → Cron ワーカーの順にデプロイする。公開サイトは Cloudflare の Workers Builds が Git 連携でビルドしてデプロイする。

どちらも、関係するファイルが変わったときだけ動く。

| 動くもの | 動かない変更 | 決めている場所 |
|---|---|---|
| GitHub Actions の「Deploy」 | `*.md` と `.claude/` の中**だけ**を変えた push（1つでもほかのファイルが変わっていれば動く。マイグレーションのファイルだけの変更でも動く） | `deploy.yml` の `paths-ignore` |
| 公開サイトのビルド（Workers Builds） | `apps/site/`、`packages/shared/`、`pnpm-lock.yaml` のどれも変えていない push | Cloudflare のダッシュボードの Build watch paths（下の「初回の準備」の手順5） |

- 「Deploy」の手動実行（Actions → Deploy → Run workflow）と、記事の公開のあとのビルド（デプロイフック）は、変わったファイルに関係なく動く
- `.md` や `.claude/` の中のファイルを、ビルドや実行時に読むようにしたら、`deploy.yml` の `paths-ignore` から外す（外さないと、その変更が本番に出ない）
- `wrangler` はルートの `package.json` の devDependency で版を固定している。Actions も、手元の `pnpm --filter @wiki/api deploy` なども、Workers Builds の `npx wrangler deploy` も、その版を使う（`npx wrangler` は、版を付けなければ、リポジトリに入っている Wrangler を使う）。版を上げると3つの Worker のデプロイすべてに効く。Workers Builds が実際に使った版は、ビルドのログの先頭に出る

| 対象 | 置き場所 | 設定ファイル |
|---|---|---|
| 管理画面 + API | Cloudflare Workers `wiki-admin`（静的アセット + Hono）。DB へは Hyperdrive 経由 | `apps/api/wrangler.toml` |
| Cron ワーカー | Cloudflare Workers `wiki-worker`（5分間隔。やることが無ければ API を呼ばない。ほかに、1日1回の版の間引きと、運用コストの取得） | `apps/worker/wrangler.toml` |
| 公開サイト | Cloudflare Workers `wiki-site`（静的アセット + `Host` で wiki を振り分ける Worker。Workers Builds が Git 連携でビルドし、記事の公開時はワーカーがデプロイフックを叩く） | `apps/site/wrangler.toml` |
| DB | マネージド PostgreSQL（Neon など） | — |
| 画像 | Cloudflare R2 のバケット `wiki-images`（`wiki-admin` と `wiki-site` の両方がバインディング `IMAGES` で使う） | 両方の `wrangler.toml` |
| Cron への印 | Cloudflare Workers KV の名前空間 `wiki-cron-marks`（`wiki-admin` が書き、`wiki-worker` が読む。どちらもバインディング `CRON_MARKS`） | 両方の `wrangler.toml` |

管理画面と API は同じ Worker が同一オリジンで出す（`/api/*` が API、それ以外は管理画面）。サイトのビルドとワーカーが使う `/export/*` `/internal/*` も同じオリジンにある。

`/export/*` と `/internal/*` は、呼ぶ側ごとに別のトークンで守る。片方が漏れても、もう片方の経路は通らない。

| トークン | 通る経路 | 持つところ |
|---|---|---|
| `EXPORT_TOKEN` | `GET /export/public`（公開中と限定公開の本文を読む。限定公開の key を含む） | `wiki-admin` のシークレット、`wiki-site` の**ビルドの**環境変数 |
| `CRON_TOKEN` | `/internal/*`（下書きを版にする、予約の実行、公開ビルドの起動、版の間引き） | `wiki-admin` と `wiki-worker` のシークレット |

公開サイトの Worker（`wiki-site`）は、実行時にはどちらのトークンも持たない（API を呼ばない）。

### 初回の準備

1. **PostgreSQL** を用意し、接続文字列を控える（プーラーを通さない直接接続のもの。`channel_binding=require` は付けない）
   - 拡張 **pg_trgm** を使う（管理画面の検索の索引）。マイグレーションが `CREATE EXTENSION IF NOT EXISTS pg_trgm` を流すので、マイグレーションのユーザーに拡張を作る権限が要る（Neon は pg_trgm に対応している）。権限が無い環境では、権限のあるユーザーで先に作っておく
   - DB の文字の種類の設定（`datctype`）が `C` だと、日本語から trigram が取れず、索引が効かない（検索の結果は変わらない）。`select show_trgm('日本語の検索')` が空でない配列を返せばよい
2. **Hyperdrive** をその接続文字列で作り（キャッシュは無効にする）、ID を `apps/api/wrangler.toml` の `[[hyperdrive]]` に入れる
3. **R2 のバケット** `wiki-images` を作る（`npx wrangler r2 bucket create wiki-images`）。公開アクセス（r2.dev や独自ドメイン）は有効にしない。画像は Worker が配る
4. **Google OAuth クライアント**を作り、承認済みリダイレクトURIに `https://wiki-admin.hatchery-works.com/api/auth/google/callback` を登録する
5. **公開サイトの Worker**（`wiki-site`）を Cloudflare の Workers Builds（Git 連携）につなぐ。Worker の名前は `apps/site/wrangler.toml` の `name` と一致させる
   - ルートディレクトリ `apps/site`、ビルドコマンド `pnpm install --frozen-lockfile && pnpm build`、デプロイコマンド `npx wrangler deploy`、ブランチ `main`。`main` 以外のブランチのデプロイコマンドは `npx wrangler preview`（`apps/site/wrangler.toml` に `[previews]` ブロックが要る）
   - ビルドの環境変数：`API_ORIGIN`（`https://wiki-admin.hatchery-works.com`）`EXPORT_TOKEN`（手順6の同じ名前のシークレットと同じ値。「シークレット」として入れる）`SITE_BASE_DOMAIN`（`hatchery-works.com`）。サイト名とオリジンは、wiki の表示名と key から決まる
   - **`main` 以外のブランチのビルド（プレビュー）は、API を呼ばず、サンプルデータ（`apps/site/fixtures/manifest.sample.json`）で作る**。プレビューの URL（`*.workers.dev`）には作ったときの内容が残るので、本番の内容（限定公開の本文と key を含む）で作ると、限定公開の URL を発行し直しても、非公開に戻しても、プレビューには残ってしまうため。ビルドの環境変数は1組で、本番のビルドとプレビューのビルドで分ける設定は Cloudflare のドキュメントに無い（プレビューにも `EXPORT_TOKEN` が渡るものとして扱う）ので、ビルドのスクリプトが、Workers Builds の入れるブランチ名（`WORKERS_CI_BRANCH`）を見て決める（`apps/site/scripts/manifest-source.mjs`）。本番のブランチを `main` から変えるときは、そのファイルの `PRODUCTION_BRANCH` も変える
   - wiki は `{key}.hatchery-works.com` で公開する。カスタムドメインはワイルドカードを使えないので、ゾーンのルート `*.hatchery-works.com/*` で受ける（`apps/site/wrangler.toml`）。**DNS に、プロキシを有効にしたワイルドカードのレコード（`*.hatchery-works.com`）を1つ足す**（行き先は使われないので、`AAAA` で `100::` など）。wiki を作るたびに DNS や設定を足す必要は無い
   - このルートは `wiki-admin` など、ほかの Worker のサブドメインにも当たる。wiki の key として使えないホスト名（予約語）は、公開サイトの Worker がそのまま本来の Worker へ渡す。**新しい Worker を同じゾーンのサブドメインで出すときは、その名前を `RESERVED_WIKI_KEYS` に足す**
   - ルートは、同じホスト名のカスタムドメインより先に当たる（[Routes](https://developers.cloudflare.com/workers/configuration/routing/routes/)）。そのままだと、管理画面へのリクエストはどれも `wiki-site` を経てから `wiki-admin` に届き、Worker の呼び出しが2回になる。**`wiki-admin` のホストをルートから外すには、ダッシュボードの `hatchery-works.com` → Workers Routes で、ルート `wiki-admin.hatchery-works.com/*` を Worker なし（None）で足す**（より細かいルートが優先され、Worker の付いていないルートは、粗いルートを打ち消す）。足したあと、管理画面が今までどおり開けることを確かめる
   - `/_astro/*`（Astro のスクリプトとスタイル）だけは、Worker を通さずに静的アセットから返す（`apps/site/wrangler.toml` の `run_worker_first`）。Worker の呼び出しに数えられず、ブラウザに1年キャッシュさせる。ここに足したパスは Host による wiki の振り分けを通らず、管理画面のホスト（上のルートを外していないとき）でも `wiki-site` のファイルが返るので、wiki ごとの内容が出るパスと、ほかの Worker が使うパスは足さない
   - **Build watch paths**（Settings → Builds → Build watch paths）を次のとおりにする。既定（Include が `*`、Exclude が空）のままだと、管理画面や API だけを変えた push でも、全 wiki・全ページをビルドし直す

     | 欄 | 入れるもの |
     |---|---|
     | Include paths | `apps/site/*`、`packages/shared/*`、`pnpm-lock.yaml` |
     | Exclude paths | `*.md` |

     - パスはリポジトリのルートから書く（ルートディレクトリの `apps/site` からではない）。`*` は0文字以上の文字に当たる。書き方は Cloudflare のドキュメントの例（`project-a/*`、`docs/README.md`）に合わせてあり、GitHub Actions の `**` は使わない
     - Exclude が先に効く。`apps/site/README.md` だけの変更ではビルドしない
     - `main` 以外のブランチのビルド（プレビュー）にも同じ設定が効く。プレビューが使うサンプルデータ（`apps/site/fixtures/`）と、ビルドのスクリプト（`apps/site/scripts/`）は `apps/site/*` に入っている
     - デプロイフックからのビルド（記事の公開・非公開、wiki の設定の変更のあと）は、この設定に関係なく動くはず。watch paths は push に含まれるファイルを見て決めるもので、デプロイフックは push を伴わない「手動のビルド」として動く。ただし Cloudflare のドキュメントに「デプロイフックには効かない」と書いた箇所は無いので、設定したら下の3つを必ず確かめる
     - 1回の push に 20 個以上のコミットか 3000 個以上のファイルの変更があると、パスに関係なくビルドされる
     - 公開サイトのビルドが、ここに無い場所のファイルを読むようにしたら（`packages/` に新しいパッケージを足して `apps/site` から使う、など）、Include paths に足す
     - 設定したあとに確かめる：README だけを変えた push でビルドが始まらない。`apps/site` を変えた push でビルドが始まる。**記事を1つ公開し直すとビルドが始まる**（始まらなければ、Include paths を `*` に戻す。戻さないと、記事の公開が公開サイトに出ない）
   - つないだらデプロイフック（Settings → Builds → Deploy Hooks、ブランチ `main`）を発行する
6. GitHub の Settings → Secrets and variables → Actions に次を登録する

   | Secret | 内容 |
   |---|---|
   | `CLOUDFLARE_API_TOKEN` | 「Edit Cloudflare Workers」テンプレートの API トークン（対象ゾーンに `hatchery-works.com` を含める） |
   | `CLOUDFLARE_ACCOUNT_ID` | Cloudflare のアカウントID |
   | `DATABASE_URL` | 手順1の接続文字列（マイグレーション用） |
   | `SESSION_SECRET` | 32文字以上のランダム文字列（`openssl rand -base64 48`） |
   | `ADMIN_EMAILS` | 最初のオーナーにする Google アカウント（カンマ区切り）。ユーザーが1人もいないときのマイグレーションで一度だけ読む（「ユーザーを DB で持つようになったときの移行」） |
   | `GOOGLE_CLIENT_ID` `GOOGLE_CLIENT_SECRET` | 手順4のクライアント |
   | `EXPORT_TOKEN` | ランダム文字列（`openssl rand -hex 32`）。`/export/public` 用。`wiki-site` のビルドの環境変数 `EXPORT_TOKEN` と同じ値にする。`wiki-admin` のシークレットになる |
   | `CRON_TOKEN` | ランダム文字列（`openssl rand -hex 32`。`EXPORT_TOKEN` とは別の値）。`/internal/*` 用。`wiki-admin` と `wiki-worker` のシークレットになる。`wiki-site` には置かない |
   | `SITE_DEPLOY_HOOK_URL` | 手順5のデプロイフックURL |
   | `NOTIFY_WEBHOOK_URL` | 任意。予約の最終失敗と、公開ビルドの起動の失敗の通知を送る Slack 互換 Incoming Webhook |
   | `GOOGLE_SERVICE_ACCOUNT_JSON` | 任意。「アクセス解析」が Google Analytics とサーチコンソールの数字を読む、サービスアカウントの鍵（JSON の中身そのまま）。作り方は上の「アクセス解析 → 使えるようにする」。未登録でもデプロイは通り、その機能だけが「未設定」になる |

   | `NEON_API_KEY` `NEON_ORG_ID` | 任意。「コスト」が Neon の使用量を読む API キーと組織 ID。作り方は上の「運用コスト → 使えるようにする」。未登録でもデプロイは通り、その機能だけが「未設定」になる |
   | `ROUTINE_TOKEN_KEY` | 任意。「全体の管理」の「Routine」のトークンを暗号化する鍵（`openssl rand -base64 48`。32文字以上。`SNS_TOKEN_KEY` とは別の値）。作り方は上の「Routine → 使えるようにする」。未登録でもデプロイは通り、その機能だけが「未設定」になる。**あとから変えない**（登録済みのトークンが使えなくなる） |
   | `X_CLIENT_ID` `X_CLIENT_SECRET` `SNS_TOKEN_KEY` | 任意。「SNS 連携」用：X の開発者アプリの OAuth 2.0 の Client ID / Client Secret と、トークンを暗号化する鍵（`openssl rand -base64 48`。32文字以上）。作り方は上の「SNS 連携 → 使えるようにする」。未登録でもデプロイは通り、その機能だけが「未設定」になる。**`SNS_TOKEN_KEY` は、あとから変えない**（つないであるアカウントが使えなくなる） |

7. リポジトリ変数（Variables）`DEPLOY_ENABLED` を `true` にする。これが無い間はデプロイのジョブは動かない（検査だけ走る）
   - 管理画面は、検査のジョブがビルドしたものを、デプロイのジョブがそのまま使う（成果物 `admin-dist`。7日で消える）。それより前の実行の「デプロイのジョブだけ」をやり直すと、成果物が無くて止まるので、そのときは「Re-run all jobs」でやり直す
8. 任意。管理画面の「アクセス解析」を使うなら、**Google のサービスアカウント**を作り、鍵を `GOOGLE_SERVICE_ACCOUNT_JSON` として登録する（Google Cloud で Google Analytics Data API と Google Search Console API を有効にする → サービスアカウントと鍵（JSON）を作る → 手順6の表のシークレットに登録する → 「Deploy」を実行する）。くわしくは上の「アクセス解析 → 使えるようにする」。あとから行ってもよい
9. 任意。5分おきの Cron が、やることの無いときに DB を起こさないようにするなら、**Workers KV の名前空間**を作る（`npx wrangler kv namespace create wiki-cron-marks`）。出力された `id` を、`apps/api/wrangler.toml` と `apps/worker/wrangler.toml` の**両方**の `[[kv_namespaces]]`（コメントにしてある3行）に入れ、コメントを外す
   - ここに、Cron への印を置く（下の「既定として選んだこと → 編集の無い時間帯は、Cron が DB を起こさない」）
   - あとから行ってもよい。コメントのあいだは、Cron が5分おきに API を呼ぶ（動きは変わらず、DB が止まれないだけ）
   - **ワーカーの側だけに入れない**。API が印を書かないので、下書きが版になるのも、予約の実行も、公開ビルドの起動も、1時間に1回になる。API の側だけに入っているぶんには害は無い
   - 実在しない `id` のままコメントを外すと、`wrangler deploy` が失敗する（`main` に入れる前に、名前空間を作って `id` を入れる）
   - 入れたあとの最初の1時間は、入れる前からあった下書き・予約に印が無いので、毎時0分の回まで待つことがある

シークレットはデプロイのたびに GitHub から Worker へ入れ直す（値を変えたら Actions の「Deploy」を手動実行する）。

### 内部のトークンを分けたときの移行

1つの `INTERNAL_TOKEN` を、`EXPORT_TOKEN`（`/export/public`）と `CRON_TOKEN`（`/internal/*`）に分けた。API は、デプロイされた時点から `INTERNAL_TOKEN` を通さない（両方を通す期間は無い）。次の順で行う。

1. **`main` に入れる前に**、値を2つ作る（`openssl rand -hex 32` を2回。別々の値にし、`INTERNAL_TOKEN` の値は使い回さない）
2. **`main` に入れる前に**、GitHub の Settings → Secrets and variables → Actions に `EXPORT_TOKEN` と `CRON_TOKEN` を登録する
3. **`main` に入れる前に**、Cloudflare の `wiki-site` → Settings → Build → Variables and secrets に `EXPORT_TOKEN` を足す（2 の `EXPORT_TOKEN` と同じ値。「シークレット」にする）。`INTERNAL_TOKEN` はまだ消さない
4. `main` に入れる。Actions の「Deploy」が、管理画面+API → Cron ワーカーの順に入れ替える
   - 公開サイトのビルド（Workers Builds）は、`main` に入ると同時に走り、API のデプロイより先になることがある。そのビルドは新しいトークンで古い API を呼ぶので `401` で失敗する（公開サイトは、前のデプロイのまま見られる）。**「Deploy」が終わったあと、`wiki-site` の失敗したビルドをやり直す**（Deployments → 失敗したビルド → Retry。記事を1つ公開し直してもよい）
   - API が入れ替わってから Cron ワーカーが入れ替わるまでの数十秒に5分おきの回が当たると、その1回は `401` で失敗する（ログに出るだけで、次の回に行われる）
5. 確かめる：`wiki-site` の `main` のビルドが通る。`wiki-worker` のログ（5分おき）に `401` が出ていない。記事を公開すると公開サイトに出る
6. 片付ける
   - GitHub のシークレット `INTERNAL_TOKEN` を消す
   - `wiki-site` のビルドの環境変数 `INTERNAL_TOKEN` を消す
   - Worker に残ったシークレットを消す：`npx wrangler secret delete INTERNAL_TOKEN --name wiki-admin`、`--name wiki-worker`、`--name wiki-site`（`wiki-site` の実行時のシークレットは、閲覧数を1件ずつ API へ送っていた頃のもの。無ければ「見つからない」と出るだけ）
7. プレビューを片付ける。これまでのプレビュー（ブランチごとの `*.workers.dev`）は、作ったときの本番の内容（限定公開の本文と key を含む）を持っていることがある
   - 持っているかどうかは、`wiki-site` → Deployments で、`main` 以外のブランチの過去のビルドのログを開くと分かる。`manifest: wiki: 12 pages, 3 unlisted` のように本番の件数が出ていれば、本番の内容で作られている（`failed to fetch manifest` や `set MANIFEST_PATH, ...` で失敗していれば、作られていない）
   - `wiki-site` → Settings → Builds に「Set up Worker Previews」の案内が出ていれば、古い方式のプレビュー（ブランチのビルドが、本番の設定のまま Worker の版と URL を作る）のまま。その場合は下の `wrangler preview delete` では消せないので、Deployments の版の一覧から、ブランチのビルドでできた版を消す
   - `wiki-site` のプレビューの一覧（ダッシュボードの `wiki-site` → Previews）を見て、残っているものを消す：`cd apps/site && npx wrangler preview delete --name <プレビューの名前>`。開いている PR のぶんは、ブランチに push し直せばサンプルデータで作り直される
   - プレビューを消しても、その前に限定公開の URL を見た人がいたかどうかは分からない。漏れては困る限定公開のページがあれば、管理画面で限定公開の URL を発行し直す

**入れ忘れたとき**

| 忘れたもの | 起きること |
|---|---|
| GitHub の `EXPORT_TOKEN` か `CRON_TOKEN` | 「Deploy」が `missing secrets` で止まる（マイグレーションのあと、API のデプロイの前）。API は古いままなので、Cron は今までどおり動く。公開サイトのビルドは、3 を済ませていれば `401` で失敗し、済ませていなければ `set MANIFEST_PATH, or API_ORIGIN and EXPORT_TOKEN` で失敗する（公開サイトは前のデプロイのまま見られるが、記事の公開が反映されない）。登録して「Deploy」をやり直す |
| `wiki-site` のビルドの `EXPORT_TOKEN` | 公開サイトの `main` のビルドが `set MANIFEST_PATH, or API_ORIGIN and EXPORT_TOKEN` で失敗し続ける（記事の公開が反映されない）。足してビルドをやり直す |
| GitHub と `wiki-site` で `EXPORT_TOKEN` の値が違う | 公開サイトの `main` のビルドが `failed to fetch manifest: 401` で失敗し続ける |

### wiki が1つだった頃からの移行

マイグレーション（`0005_multi_wiki`）が、いまある行をすべて最初の wiki（`key = wiki`）に入れる。公開中の URL は変わらない。次の順で行う。

1. DNS にワイルドカードのレコード（`*.hatchery-works.com`、プロキシ有効）を足す
2. Workers Builds のビルドの環境変数に `SITE_BASE_DOMAIN`（`hatchery-works.com`）を足す（`SITE_ORIGIN` と `SITE_NAME` は使わなくなるので、あとで消してよい）
3. `main` に入れる。マイグレーション → 管理画面+API → Cron ワーカーの順にデプロイされる
4. **管理画面の「全体の管理」の「wiki」タブで、最初の wiki の表示名を、これまでの `SITE_NAME` と同じ名前に直す**。移行の直後の表示名はツリーの名前（`trees.name`。変えていなければ「メイン」）になっている。`SITE_NAME` は公開サイトのビルドの環境変数で、マイグレーションからは読めないため。表示名を直すと公開サイトがビルドし直される
5. 公開サイト（`wiki-site`）のデプロイが済んだら、`wiki.hatchery-works.com` が今までどおり見られることを確かめる。カスタムドメイン `wiki.hatchery-works.com` の設定が Cloudflare に残っていれば外す（ルートに置き換わった）

公開サイトは、`apps/site` か `packages/shared` を変えた push が `main` に入るとすぐビルドされ、API のデプロイより先になることがある。そのときは wiki が1つだった頃の形のデータを、最初の wiki 1つ分としてビルドする（サイト名は「wiki」、テーマは既定。`apps/site/scripts/fetch-manifest.mjs`）ので、ビルドは失敗しない。逆に、API のデプロイのあと 4 より前にビルドされると、サイト名がツリーの名前で出る。気になる場合は、3 の前に Workers Builds を一時停止し、4 のあとで再開する。

### ユーザーを DB で持つようになったときの移行

`ADMIN_EMAILS` の許可リストから、DB のユーザーに移した（マイグレーション `0019_users_and_invites`）。

1. `main` に入れる。マイグレーション（`pnpm db:migrate`）が、ユーザーが1人もいなければ `ADMIN_EMAILS` のメールアドレスを**オーナーとして登録**し、最初の wiki の管理者にする。この時点では Google のアカウント ID が分からないので、メールアドレスだけの行を作り、最初のログイン（確認済みのメールアドレスが一致）で結びつける
2. いまのセッションはすべて無効になる。Google でログインし直す。スターと本文の下書きは、メールアドレスで持っていたものをユーザーに結びつけ直すので、そのまま残る
3. 移行が本番に入ったのを確かめたら、次のデプロイで `.github/workflows/deploy.yml` の Migrate database の `ADMIN_EMAILS` と、GitHub のシークレット `ADMIN_EMAILS` を消す（2回目からは読まないので、残っていても害は無い）。Worker に残ったシークレットは `wrangler secret delete ADMIN_EMAILS` で消せる

手元から出す場合は `wrangler login` のうえで `pnpm --filter @wiki/admin build && pnpm --filter @wiki/api deploy`、`pnpm --filter @wiki/worker deploy`。

## サイドバーのツリーの取得の計測

管理画面のサイドバーは、`GET /structure` で wiki 全体のツリーとページの情報を1回で取る（issue #232）。ページ数を変えて測ったところ、10,000 ページでも足りていたので、分けて取る作り替えはしていない。

測り方: PGlite の API に、ページ N 件（10 件に 1 件が公開済み、ルート 10 件、各ページの子は最大 8 件、深さ 3〜4）を作り、`GET /structure` を 5 回呼んだ中央値。管理画面は、ヘッドレス Chrome で開いてから最初のツリーの行（`[role="treeitem"]`）が出るまで。

| ページ数 | `loadCommit` | ページの `select` | API 全体 | 問い合わせ数 | JSON | gzip | 管理画面でツリーが出るまで |
|---|---|---|---|---|---|---|---|
| 100 | 1.1ms | 0.9ms | 5.5ms | 6 | 26KB | 3.4KB | 未計測 |
| 500 | 6.2ms | 5.2ms | 14ms | 6 | 132KB | 16.5KB | 未計測 |
| 2,000 | 7.7ms | 7.5ms | 34ms | 6 | 532KB | 65KB | 未計測 |
| 10,000 | 37.5ms | 37.7ms | 165ms | 6 | 2.7MB | 320KB | 約 0.55〜0.66 秒（うち `GET /structure` が約 0.2 秒） |

- 問い合わせ数はページ数によらず 6 回で一定。増えるのは応答時間とサイズだけ
- 本番の Postgres とネットワークは測れていない。メモリ内の DB で、vite のプロキシ経由（圧縮なし）の値
- 将来分ける必要が出たら、候補は「構造（親子と並び）は全部取り、ページの情報だけあとから取る」と「階層ごとに取る」。どちらも、`["structure"]` を使うほかの画面（コマンドメニュー、公開パネル、メンション、履歴、削除、テンプレート、編集画面）と、ドラッグでの並べ替えに手を入れることになる

## ローカル開発

Node 22 と pnpm、PostgreSQL（拡張 pg_trgm を作れること。ふつうは contrib に入っている）が必要。

```sh
pnpm install
cp apps/api/.env.example apps/api/.env   # DATABASE_URL, SESSION_SECRET, DEV_LOGIN_EMAIL を設定
pnpm db:migrate                          # マイグレーション + 最初の wiki のツリー（空）の初期化（ADMIN_EMAILS をオーナーに）
pnpm db:seed                             # テスト用データを投入（任意。ページが1件も無いときだけ入る）
pnpm dev                                 # API :8787 と管理画面 :5173
```

公開サイトはサンプルデータでビルドできる（APIなしで確認できる）：

```sh
pnpm --filter @wiki/site build:sample   # dist/ に出力し、限定公開の漏れなどを検査
```

APIのデータでビルドする場合は `API_ORIGIN=http://localhost:8787 EXPORT_TOKEN=... pnpm --filter @wiki/site build`（`apps/api/.env` の `EXPORT_TOKEN` と同じ値）。手元では `Host` で wiki が決まらないので、表示する wiki は `?wiki={key}`（`pnpm preview`）か環境変数 `WIKI`（`astro dev`）で選ぶ（`apps/site/README.md`）。

テスト用データ（`pnpm db:seed`）は、3段の階層に公開・限定公開・予約・下書き・公開後に編集ありのページを一通り含む。2つめの wiki（`notes`「開発ノート」）にも数ページ入るので、wiki の切り替えを確かめられる。ユーザーは、最初の wiki の管理者（`sakura@example.com`）と編集者（`minato@example.com`、2つめの wiki にも編集者として入る）を足す（Google でログインすることは無く、メンバーの画面の確認用）。既存のデータを消して入れ直す場合は `pnpm db:seed --reset`（すべてのテーブルを空にするので、ローカル専用。`NODE_ENV=production` では動かない）。

`DEV_LOGIN_EMAIL` を設定すると、Googleを通さない「開発用ログイン」ボタンが出て、そのメールアドレスのユーザーをオーナーとして作ってログインする（`NODE_ENV=production` では無効）。
Googleログインを試す場合は OAuth クライアントを作り、承認済みリダイレクトURIに `http://localhost:5173/api/auth/google/callback` を登録する。
MCP は `http://localhost:5173/mcp` でつなげる（管理画面の開発サーバーが `/oauth` `/.well-known/oauth-*` `/mcp` を API へ渡す）。例：`claude mcp add --transport http wiki-local http://localhost:5173/mcp`。

テスト・型チェック（DBはPGliteで動くのでPostgreSQL不要。PGlite を自分で立てるときは、`new PGlite({ extensions: { pg_trgm } })` のように pg_trgm を読み込む。`apps/api/src/test/harness.ts` の `pgliteExtensions`）：

```sh
pnpm typecheck
pnpm test
```

スキーマを変えたら `pnpm db:generate` でマイグレーションを生成する。

### E2E テスト（`apps/e2e`）

管理画面をブラウザで操作して確かめる（Playwright）。管理画面はビルドした成果物を、本番と同じく API の Worker（`wrangler dev` の `[assets]`）から配る。DB は PostgreSQL（`wrangler dev` の Hyperdrive は TCP の PostgreSQL にしかつなげないので、PGlite は使えない）。手元の開発用とは別の DB を作っておく。

```sh
createdb wiki_e2e                                   # 既定の接続先は postgres://postgres:postgres@localhost:5432/wiki_e2e（E2E_DATABASE_URL で変える）
pnpm --filter @wiki/admin build                     # 配る管理画面（E2E_ADMIN_DIST で別のディレクトリを指定できる）
pnpm --filter @wiki/e2e exec playwright install chromium
pnpm --filter @wiki/e2e e2e                         # マイグレーションしてから :8789 で立て、開発用ログインで入って確かめる
```

- DB は実行をまたいで残る（テストはページのタイトルに時刻を入れて見分ける）
- CI では、PR が管理画面か API に影響するときだけ走る（`ci.yml` の `e2e`）。管理画面を変えていない PR では、`main` でビルド済みの管理画面（Actions のキャッシュ `admin-dist-<sha>`。`main` への push の `check` が残す）を使い、ビルドを省く。マージ先との分かれ目のコミットから、管理画面に影響する変更の無い範囲をさかのぼって探し（`scripts/ci-admin-dist-keys.sh`）、見つからなければビルドする。どれを使ったかは実行の Summary に出る

## 既定として選んだこと（設計書の未決事項）

- **API/DBのホスティング**：Hono を Cloudflare Workers + Hyperdrive で動かし、DBはマネージドPostgreSQL（Neon等）を想定。コードはランタイム非依存（`createApp(deps)`）にしてあり、ローカルはNode（`src/node.ts`）、本番は Workers（`src/worker.ts`）で動かす
- **予約の通知先**：最終失敗は Slack 互換の Incoming Webhook（`NOTIFY_WEBHOOK_URL`）へ。メールは未対応
- **予約の反映遅延**：Cron 5分 + デバウンス2分 + ビルド時間
- **編集の無い時間帯は、Cron が DB を起こさない**：5分おきの Cron は、API を呼ぶ前に Workers KV の印（バインディング `CRON_MARKS`）だけを見て、時刻の来た印が無ければそこで終わる（API を呼ぶと DB につながり、サーバーレスの PostgreSQL が自動で止まれなくなる）
  - 印は4つ。値は `{"at":"<ISO の時刻>"}` で、「この時刻になったら DB を見に行く」の意味

    | キー | 書くとき（API） | 時刻 |
    |---|---|---|
    | `cron:drafts` | 下書きの保存 | いちばん早く版にできる時刻（最後の保存から5分か、始めてから30分の早い方） |
    | `cron:scheduled` | 予約の登録・時刻の変更 | 次に実行する予約の時刻 |
    | `cron:build` | 公開イベントの記録（`recordPublishEvent`） | 書いた時刻（次の Cron で見る） |
    | `cron:workflow` | ワークフローの実行を積んだとき（`enqueue.ts`） | 積んだ時刻。処理のあとは、再試行待ち・通知待ちの失敗があれば次の回、動いている実行は「落ちた」と見なす時刻（動かしてから10分） |

  - API は、印が無いか、いまの印より早い時刻のときだけ書く（下書きの自動保存のたびには書かない）。書くのは応答ができたあと（DB のコミットのあと。`apps/api/src/cron/marks.ts`）。消すことはしない
  - ワーカーは、時刻の来た印を消してから `/internal/tick` を呼び、応答の `next`（処理のあとで DB から求めた、次に見に行く時刻）で印を書き直す。残りが無い種類の印は消えたままになる。API の呼び出しが失敗したら、消した印を戻す（`apps/worker/src/tick.ts`）
  - 「ビルド待ちあり」の印は、デバウンス中と、デプロイフックを呼べていないあいだ残る。フックを呼べた回でも消さず、次の回に API が「変更なし」と答えたところで消える（公開のあと、DB を見る回が1回余分にある）
  - 印を消した回の次の回は、印に関係なくもう一度 API を呼ぶ（ワーカーだけが使う印 `cron:recheck`）。KV の読み出しは最大60秒ほど古いことがあり、そのあいだに API が「消す前の印」を読むと、印はもうあると思って書かずに終わるため。その変更は DB にはあるので、次の回に拾う。見直しの回は何も消さないので、続くことはない（編集が止まったあと、DB を見る回が1回余分にある）
  - KV に書いた印がワーカーから見えるまでにも最大60秒ほどかかるので、Cron の直前に書いた印は、次の回に回ることがある。どちらの場合も、遅れは Cron 1回分（5分）まで
  - **1時間に1回（毎時0分の回）は、印に関係なく API を呼ぶ**。印を書き損ねた（KV への書き込みの失敗、ワーカーが印を消したあと書き直す前に落ちた）ときは、ここで拾う。そのとき遅れるのは最大1時間
  - バインディングが無い環境（手元の開発、テスト、KV の名前空間を作る前）では、API は印を書かず、ワーカーは今までどおり5分おきに API を呼ぶ
- **公開ビルドの起動の失敗**：デプロイフックを呼べなかったビルドは、次の Cron（5分後）で、新しい公開操作が無くても起動し直す（`site_builds.triggered_at` が空のあいだ。ワーカーはフックを呼べたら `/internal/builds/{id}/triggered` で埋める。起動できるまで「ビルド待ちあり」の印が残るので、編集が無くても次の Cron は API を呼ぶ）。同じビルドの起動が3回続けて失敗したら、予約の最終失敗と同じ通知先へ一度だけ知らせ、そのあとも5分おきに試し続ける。Workers Builds の側でビルドが失敗したことは検知しない
- **管理画面とAPIは同一オリジン**（管理画面の `/api/*` をAPIへ）。Cookieは `SameSite=Lax`、状態を変えるリクエストは `Origin` が管理画面と一致する場合のみ受け付ける
- **ツリーそのものの設定は無い。** ツリーは常に公開サイトに出し、出す・出さないはページごとの公開範囲で決める。公開サイトでの呼び名は固定（「ページ一覧」）
- **設計書に無い構造操作を1つ追加**：`remove_node`（ツリーから外す。子がある場合は不可）
- 新しいページは指定した親ページの下（指定が無ければ最上位）の末尾に入る
- **ページの削除は「ゴミ箱に入れる」**（`pages.deleted_at`）。選んだページと配下のページをまとめてツリーから外し、公開をやめ（公開したことがあるページは公開サイトで 410）、予約を取り消す。一覧・検索・スター・ツリー・公開サイトには出なくなる
  - いっしょに入れたページは1つのまとまり（`pages.trash_root_id` に、削除で選んだページの ID）。管理画面の「ゴミ箱」（`/w/{key}/trash`）に、まとまりごとに1行で出る。自動では消さず、人が完全に削除するまで残る
  - **元に戻す**：まとまりごと、親子関係と並び（`trashed_parent_id` / `trashed_position`）を保って戻す。置き場所は、元の親がツリーに残っていればその下の末尾、無ければ最上位の末尾。非公開のまま戻り、公開と予約は戻さない
  - 親をゴミ箱に入れる前に、配下の一部だけを先に入れていたら、別々のまとまりとして出る。親を戻しても、先に入れた方は戻らない
  - **完全に削除**：管理画面の人だけ（MCP の道具は無い）。まとまりごと、版・下書き・リンク・スター・予約の行を消す。`pages` の行は `purged_at` を入れて残す（公開したことがあるページを 410 にし続けるため）
  - この仕組みを入れる前に削除したページは、1ページずつのまとまりとしてゴミ箱に出る（`0014_page_trash`）。元の親は残っていないので、戻すと最上位に入る
- フォルダと Inbox があった頃のデータは `0002_pages_only` で移行する：フォルダは同名の（本文が空の非公開）ページになり、Inbox の中身は最上位に出る。ツリーに無いページは `pnpm db:migrate` の際に最上位へ入れる
